Database connection pooling

Also called: connection pool, PgBouncer, too many connections, pooler, Supavisor

Reusing a small set of open database connections instead of opening a new one for each request. Postgres handles a limited number of connections, and serverless functions can open hundreds at once, so a pooler sits in between and shares a few real connections.

You need it when

  • You run on serverless or many workers and see 'too many connections'.
  • Each request spends noticeable time connecting to the database.

Skip it when

  • One long-running server with a few workers that keep their connections open.

Ways to build it

  1. Persistent connections in your app $0

    Django CONN_MAX_AGE, or Django 5.1+'s built-in pool option with psycopg[pool], SQLAlchemy's pool, or a single shared Prisma client per process.

    Tradeoff: Enough for normal servers. Doesn't help when every function invocation is a new process.

  2. Your host's pooler $0, included

    Supabase (Supavisor), Neon and most managed Postgres providers give a pooled connection string. Use it for app traffic and the direct one for migrations.

    Tradeoff: One-line change. Transaction mode breaks session features like some prepared statements, LISTEN and advisory locks held across queries.

  3. PgBouncer $0 self-hosted

    Run PgBouncer next to Postgres in transaction pooling mode and point the app at it.

    Tradeoff: Fast and proven. One more service to run and monitor.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Fix database connection limits for this app on [host].

Requirements:
- Count the maximum connections we could open: processes or functions times pool size per process. Compare with the database's max_connections and show the math.
- Use [the host's pooled connection string / PgBouncer in transaction mode] for app traffic, and a direct connection for migrations.
- Check the code for features that break under transaction pooling (session settings, LISTEN/NOTIFY, prepared statements, advisory locks) and fix or document each.
- In serverless code, create one database client per process, not per request.
- Close or reset inherited connections after a worker forks.
- Add a health check that fails if the database can't be reached.

Acceptance checks (run each and show me the result):
1. A load test of [100] concurrent requests produces no 'too many connections' errors.
2. The connection count in pg_stat_activity stays under the planned limit during the test.
3. Migrations still run over the direct connection.
4. Nothing in the code depends on session state that the pooler would break.

If you skip it

The app goes down under a traffic spike with 'too many connections', or every request pays the connection setup time.

How Derek runs it

Custody Journal doesn't run a separate pooler. Django keeps each connection open for up to 10 minutes (conn_max_age 600), and the Gunicorn fork hooks close database and cache connections inherited from the parent process so workers never share one.
