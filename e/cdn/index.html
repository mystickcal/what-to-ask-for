CDN and static asset caching

Also called: content delivery network, static files, Cache-Control immutable, hashed filenames, edge caching

Serving files that are the same for everyone, like CSS, JavaScript, fonts and images, from servers close to the user, with file names that change when the content changes. Then browsers can cache them for a year, and a deploy still shows the new version at once.

You need it when

  • Users are spread out geographically, or your app server spends time sending static files.
  • People report seeing an old version after a deploy.

Skip it when

  • Your host already does this, as Vercel, Netlify and Cloudflare Pages do for built assets. Check the headers and move on.

Ways to build it

  1. Hashed file names and long cache headers $0

    Your bundler (Vite, Next.js, webpack) or Django's ManifestStaticFilesStorage adds a content hash to each file name. Serve them with Cache-Control: public, max-age=31536000, immutable, and keep HTML short-lived.

    Tradeoff: The base of everything else. Free.

  2. WhiteNoise or your host's static serving $0

    For Python apps, WhiteNoise serves compressed, hashed static files with the right headers straight from the app.

    Tradeoff: No extra service. Still served from one region unless a CDN sits in front.

  3. A CDN in front $0, free tiers

    Cloudflare (free plan), Bunny or CloudFront cache static files at the edge.

    Tradeoff: Fast everywhere. Misconfigured rules can cache private pages, so cache by path or header, not everything.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Set up static asset caching and a CDN for this app.

Requirements:
- Make every built CSS, JS, font and image file name include a content hash.
- Serve hashed files with Cache-Control: public, max-age=31536000, immutable.
- Serve HTML with a short cache or no-cache, so a deploy shows up at once.
- Compress text assets with Brotli or gzip.
- If a CDN is added, cache only static paths (like /static/ or /assets/) and public pages. Never cache responses that set cookies or depend on the logged-in user.
- Document how to purge the CDN if a bad file ships.

Acceptance checks (run each and show me the result):
1. curl -I on a JS file shows the immutable cache header and a hashed name.
2. curl -I on the home page shows a short or no-cache header.
3. After a deploy, a normal reload shows the new version without a hard refresh.
4. A logged-in page is never served from the CDN cache (check the CDN's cache status header).

If you skip it

Slow pages far from your server, users stuck on old JavaScript that calls APIs that no longer exist, or a CDN serving one user's page to everyone.
