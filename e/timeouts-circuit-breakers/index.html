Timeouts and circuit breakers

Also called: request timeouts, circuit breaker, fail fast, slow third-party API, cascading failure

A timeout puts a limit on how long you wait for another service. A circuit breaker watches for repeated failures and, once there are too many, stops calling that service for a while and fails right away. Together they keep one slow dependency from tying up your whole app or running up a bill.

You need it when

  • Your app calls payment, email, AI or other third-party APIs during a request.
  • You have retries, and a long outage could turn them into a flood of calls.

Skip it when

  • Calls that only happen in background jobs with their own timeout, where waiting longer is fine.

Ways to build it

  1. Timeouts on every outbound call $0

    Set a timeout in your HTTP client (requests timeout=, fetch with AbortSignal.timeout, SDK timeout options). Most clients wait forever by default.

    Tradeoff: The biggest win for the least work. Pick numbers from how slow the service really gets.

  2. A circuit breaker library $0

    opossum (Node), pybreaker (Python) or resilience4j (Java) wrapped around the calls that matter.

    Tradeoff: Stops hammering a service that is down. Another thing to tune and monitor.

  3. Move slow calls off the request $0

    Put the call in a background job, show a pending state, and let the job retry with backoff.

    Tradeoff: Users never wait on a third party. Needs a job queue and a way to show results later.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add timeouts and a circuit breaker to this app's outbound calls to [Stripe / OpenAI / email provider / other APIs].

Requirements:
- Find every outbound HTTP or SDK call and give it an explicit timeout: [5] seconds for user-facing requests, longer only where the work needs it.
- Cap retries at [2] with exponential backoff and jitter. Never retry inside a loop that is itself retried.
- Wrap [the slow or flaky service] in a circuit breaker that opens after [5] failures in a row, fails fast for [30] seconds, then lets one test call through.
- When the breaker is open, return a clear message or a fallback instead of an error page.
- Log each timeout and every time the breaker opens or closes.
- Use [opossum / pybreaker / the existing HTTP client's options].

Acceptance checks (run each and show me the result):
1. Pointing [service] at an address that never answers makes the call fail within the set timeout, not hang.
2. A slow external service doesn't make unrelated pages slow, checked with a quick load test.
3. After [5] failures in a row the breaker opens and calls fail fast without hitting the service.
4. Once the service is back, the breaker closes again on its own and calls succeed.

If you skip it

One slow API ties up every worker and your whole site goes down with it. Retries against a dead service can pile up into thousands of calls and a surprise bill.

How Derek runs it

Custody Journal sets explicit timeouts on its outbound calls: 10 seconds for each webhook delivery, with the DNS lookup capped at 5 seconds, and 60 seconds with one retry for voice memo transcription, which then tells the user to try again or type instead. It does not use a circuit breaker.
