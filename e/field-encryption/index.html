Field-level encryption

Also called: encrypt database fields, application-level encryption, encryption at rest, encrypted columns, key rotation

Encrypting chosen columns in your app before they reach the database, with a key the database never sees. A stolen backup or database dump then shows ciphertext for those fields. It needs a plan for keys, rotation and search.

You need it when

  • You store very sensitive text (health, legal, financial notes), government ids, or access tokens for other services.

Skip it when

  • Your host's disk encryption covers your threat and the data isn't especially sensitive. Fields you must search or sort on are hard to encrypt.

Ways to build it

  1. An encrypted field type in your framework $0

    Rails Active Record Encryption, Laravel encrypted casts, or a Django field built on Fernet from the cryptography package.

    Tradeoff: Transparent in code. Encrypted fields can't be filtered or sorted in SQL.

  2. Envelope encryption with a KMS low, per key and request

    AWS KMS, Google Cloud KMS or Vault wrap per-record data keys. Your app encrypts with the data key.

    Tradeoff: Strong key control and audit. More moving parts and latency.

  3. Database-side encryption functions $0

    Postgres pgcrypto encrypts in SQL.

    Tradeoff: Easy to add. The key travels to the database in queries and may show up in logs.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add field-level encryption for sensitive columns.

Requirements:
- Columns: [list]. Encrypt in the app with [Fernet / AES-GCM] before saving and decrypt on read.
- The key comes from an environment secret separate from other app secrets, never from the database.
- Prefix each stored value with a version tag so I can tell encrypted from plain and rotate keys later.
- Rotation: a new key encrypts, old keys still decrypt, and a background command re-encrypts rows in batches.
- If a value can't be decrypted, show a placeholder and keep the stored ciphertext untouched on save.
- Encrypt existing rows with a migration that runs in batches and can resume.
- For fields I need to look up exactly, store a separate keyed hash (HMAC) for lookups.
- Keep decrypted values out of logs, error reports and analytics.

Acceptance checks (run each and show me the result):
1. Reading the table directly shows ciphertext for each listed column.
2. After rotating, old rows still read and the re-encrypt command upgrades them.
3. Starting the app with the wrong key shows placeholders, not crashes, and saving doesn't destroy data.
4. Error reports contain no decrypted values.
5. A restore from backup is readable only with the key.

If you skip it

A leaked backup or read-only database breach exposes the most private data you hold.

How Derek runs it

Custody Journal encrypts sensitive text and JSON columns with Fernet before they reach Postgres, using its own field encryption key setting rather than the main app secret. Stored values carry a version prefix, older keys stay decrypt-only for rotation, and a value that can't be decrypted shows a placeholder while the original ciphertext is kept on save.
