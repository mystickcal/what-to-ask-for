Idempotent webhook handling

Also called: idempotency key, event dedupe, processed events table, event inbox, exactly-once processing

Providers retry webhooks and sometimes deliver the same event more than once or out of order. Idempotent handling means running the same event twice has the same result as running it once. The usual way: save the event id first and skip it if it's already done.

You need it when

  • You take payments or grant access based on webhooks.
  • A handler sends email, creates records or calls another paid API.

Skip it when

  • The handler only copies the latest state from the provider's API onto your record. That is already idempotent, but dedupe anyway if it also sends email.

Ways to build it

  1. A processed-events table $0

    Unique constraint on the event id. Insert first, then process, then mark complete. A recovery job replays failed or stuck rows.

    Tradeoff: Solid. You need that recovery job, or events that crash mid-way stay stuck.

  2. Re-fetch and sync state $0

    Treat the event as a hint. Fetch the subscription or order from the API and set your record to match it.

    Tradeoff: Handles out-of-order events well. Costs an API call per event and can hit rate limits.

  3. Idempotency keys on your outgoing calls $0

    Send an Idempotency-Key header on Stripe POST requests, based on your own record id, so your retries don't create a second charge.

    Tradeoff: Covers your requests to Stripe, not the events Stripe sends you. Use it with one of the above.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Make the [provider] webhook handler idempotent.

Requirements:
- After the signature check, insert the event id into a processed_events table with a unique constraint. If it already exists and is complete, return 200 and do nothing.
- Process inside a transaction and lock the affected account or subscription row.
- Mark the event complete only after the work commits. On failure, mark it failed with a next retry time and return 500 so the provider retries.
- Add a recovery job that replays failed events and events stuck in processing past a lease time.
- For outgoing Stripe POSTs that create charges or subscriptions, send an Idempotency-Key based on our own record id.

Acceptance checks (run each and show me the result):
1. Sending the same signed event twice gives one upgrade, one email and one row.
2. Two copies sent at the same moment still give one result.
3. An event that throws once is retried, succeeds, and its effect happens once.
4. subscription.deleted arriving before subscription.updated still leaves the right final state.
5. Retrying our own create call with the same Idempotency-Key does not make a second charge.

If you skip it

Double upgrades, double emails, duplicate orders, or a canceled customer who keeps access.

How Derek runs it

Custody Journal stores each verified Stripe event in a row keyed by the event id before doing any work. Processing locks that row, takes a 3 minute lease and marks it complete only after the work succeeds. A failure is scheduled for retry 2 minutes later and the endpoint returns 500. A replay job picks up failed or stuck events, and a separate daily job reconciles subscriptions.
