Data retention and cleanup

Also called: retention policy, data minimization, purge old data, TTL cleanup, log retention

A written list of what data you keep, for how long and why, plus scheduled jobs that delete or anonymize it when time is up. It covers logs, backups, temporary files, expired tokens and closed accounts.

You need it when

  • You store personal data, logs or files. Privacy laws such as GDPR expect you not to keep data longer than needed.
  • Tables like sessions, events and logs grow forever.

Skip it when

  • Never. Even a short policy with two cleanup jobs beats none.

Ways to build it

  1. Scheduled delete jobs $0

    A daily job per data type deletes rows older than the limit, in small batches.

    Tradeoff: Simple and visible. Each new table needs its own rule.

  2. Built-in expiry $0

    Redis key TTLs, object storage lifecycle rules (S3, R2), log platform retention settings, and Postgres partition dropping for big time-series tables.

    Tradeoff: Hands-off once set. Easy to forget backups and copies.

  3. Anonymize instead of delete $0

    Remove or hash personal fields but keep aggregate rows for reporting.

    Tradeoff: Keeps stats. Make sure it can't be re-identified.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Write and apply a data retention policy for my app.

Requirements:
- List every place data is stored: tables, file storage, logs, backups, analytics, error tracking, email provider, AI provider.
- For each: what's kept, why, how long ([30 days / 1 year / until account deletion]), and delete or anonymize.
- Add a scheduled job per rule that deletes in batches with a row limit per run and logs counts.
- Set TTLs or lifecycle rules where the platform supports them (Redis, object storage, logs).
- Make sure backups roll off within a stated window, and note it in the privacy policy.
- When an account is deleted, cover every store in the list.
- Produce the policy as a short page I can link from the privacy policy.

Acceptance checks (run each and show me the result):
1. Rows older than each limit are gone after the job runs.
2. Each cleanup job logs how many rows it removed.
3. Bucket lifecycle rules show the stated expiry.
4. The policy page matches what the jobs actually do.
5. A deleted test account leaves nothing in the listed stores beyond backups, which roll off on schedule.

If you skip it

You keep years of personal data you don't need, which raises breach damage, storage cost and legal risk.
