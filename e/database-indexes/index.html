Database indexes

Also called: slow query, query optimization, EXPLAIN ANALYZE, composite index, N+1 queries

Lookup structures that let the database find rows without reading the whole table. Most slow pages in young apps come from a missing index on the columns a query filters and sorts by, or from N+1 queries that run one query per row.

You need it when

  • Pages get slower as tables grow past tens of thousands of rows.
  • Your query log shows the same query running once per item in a list.

Skip it when

  • Tiny tables. Extra indexes slow down writes and take space, so add them for real queries, not just in case.

Ways to build it

  1. Measure, then index what queries use $0

    Turn on pg_stat_statements (Postgres) or your framework's query log, find the slowest and most frequent queries, run EXPLAIN ANALYZE, and add an index matching the WHERE and ORDER BY columns.

    Tradeoff: Fixes the real problems. Needs production-like data to see them.

  2. Composite and partial indexes $0

    One index on (user_id, created_at) serves 'this user's newest items'. A partial index (WHERE deleted_at IS NULL) keeps it small.

    Tradeoff: Column order matters: equality filters first, then the sort column.

  3. Fix N+1 queries $0

    Load related rows in one query: select_related and prefetch_related (Django), include (Prisma), joins or batched loaders.

    Tradeoff: Often a bigger win than any index. Tools like django-debug-toolbar show the query count.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Find and fix slow database queries in this app.

Requirements:
- Turn on query logging or pg_stat_statements and list the 10 slowest and 10 most frequent queries.
- For each, run EXPLAIN ANALYZE on production-like data and show whether it uses an index.
- Add indexes that match the filters and sort order, composite where needed, with equality columns first. Note that Postgres doesn't index foreign keys automatically.
- On large tables, create indexes without blocking writes (CREATE INDEX CONCURRENTLY on Postgres).
- Find N+1 query patterns in list pages and APIs and load related data in batches.
- Report the before and after timings and the query count for the main pages.

Acceptance checks (run each and show me the result):
1. EXPLAIN ANALYZE for the main list query shows an index scan, not a sequential scan, on a large table.
2. The main list page runs a fixed number of queries no matter how many rows it shows.
3. Before and after timings are shown for each fix.
4. Each new index is used by at least one real query.

If you skip it

An app that was fast in the demo slows to seconds per page with real data, and the database bill climbs to compensate.

How Derek runs it

Custody Journal's journal entries have a composite index on (user, is_archived, newest date first), which matches the main entry list. Its email outbox has an index on (status, next attempt time, created time) so the sender can find due emails quickly.
