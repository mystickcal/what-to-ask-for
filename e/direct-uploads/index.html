Direct-to-storage uploads

Also called: presigned upload URL, signed upload URL, direct upload, browser to S3 upload, resumable upload

Your server hands the browser a short-lived signed URL, and the browser sends the file straight to object storage. Your app never holds the bytes, so big files don't tie up workers or hit request size limits. Your server still decides who can upload, what key the file gets and how big it can be.

You need it when

  • Users upload files bigger than a few MB, like photos, video or PDFs.
  • Your host caps request size or time, as most serverless platforms do.

Skip it when

  • Uploads are small and rare, and your server checks the contents anyway before storing them.

Ways to build it

  1. Presigned PUT URL storage only

    S3, Cloudflare R2, Google Cloud Storage and most S3-compatible stores can sign a PUT URL for one object key that expires in minutes. The browser PUTs the file, then tells your server it's done.

    Tradeoff: Simplest. A plain PUT URL can't enforce a size range, so check the object size after upload and delete anything too big.

  2. Presigned POST with a policy storage only

    S3's POST policy can require a content-length-range and a key prefix, so the store itself rejects files that are too big.

    Tradeoff: Enforces size up front. Not every S3-compatible store supports it. R2 presigned URLs don't support POST.

  3. Resumable uploads $0 self-hosted

    The tus protocol (tusd server, Uppy client) or S3 multipart uploads send the file in chunks and resume after a dropped connection.

    Tradeoff: Best for very large files and phones on bad networks. More moving parts.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Change [feature] so files upload straight from the browser to [S3/R2/GCS] instead of through the app server.

Requirements:
- New endpoint: the logged-in user asks for an upload. The server checks they're allowed, picks the object key itself (never from the client, e.g. uploads/<user_id>/<random>), and returns a signed URL that expires in [10] minutes.
- Limit size: use a POST policy with content-length-range if the store supports it. Otherwise check the object size when the upload is confirmed and delete it if it's over [50 MB].
- After upload, the browser calls a confirm endpoint. The server checks the object exists, records it in the database with its owner, and only then shows it in the app.
- Uploaded objects stay private. Downloads go through signed download links.
- A cleanup job deletes objects that were never confirmed after [24] hours.
- Set the bucket's CORS rules to allow PUT (or POST) only from the app's own origin.

Acceptance checks (run each and show me the result):
1. A 200 MB file uploads without the app server's memory or request time growing.
2. A file over the size limit is rejected or deleted, and never shows up in the app.
3. The signed URL stops working after it expires.
4. Changing the key in the request can't overwrite another user's file.
5. An unconfirmed upload is removed by the cleanup job.

If you skip it

Uploads fail on big files, workers stall while bytes stream through them, or a bucket left open lets anyone write to it.

People describe this as

  • “large uploads time out on my server”
  • “let users upload videos without going through my backend”
  • “my server runs out of memory when people upload files”
  • “upload straight to S3 or R2 from the browser”
