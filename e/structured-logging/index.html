Structured logging

Also called: JSON logs, log aggregation, request id, correlation id, observability

Writing logs as data, one JSON object per event with fields like event name, user id, request id and duration, instead of free text. Then you can search and count them, and follow one request through every service it touched.

You need it when

  • You debug production problems by reading logs.
  • Work for one request spans the web app, a queue and a worker.

Skip it when

  • A tiny app where error tracking covers what you need.

Ways to build it

  1. A structured logging library $0

    structlog (Python), pino (Node) or your framework's JSON formatter, writing to stdout.

    Tradeoff: Small change with a big payoff. Agree on field names early.

  2. Ship logs somewhere searchable $0 self-hosted, free tiers

    Grafana Loki or OpenSearch self-hosted, or a hosted tier like Better Stack, Axiom or your host's log search.

    Tradeoff: Search across all servers. Watch retention and volume costs.

  3. OpenTelemetry $0

    Add trace and span ids to logs and send traces too, to see a request across services.

    Tradeoff: The fullest picture. More setup than most small apps need at first.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Switch this app to structured JSON logging.

Requirements:
- Use [structlog / pino] and write one JSON object per line to stdout.
- Every line has timestamp (UTC), level, event (a short snake_case name), and request_id. Add user_id where there is one.
- Generate a request id per incoming request (or accept a trusted X-Request-ID), return it in a response header, and pass it to background jobs.
- Never log passwords, tokens, API keys, full card numbers or message bodies. Add a filter that drops known sensitive keys.
- Replace print statements and string-formatted log lines in [modules] with events.
- Log the duration and status of each request at info level.

Acceptance checks (run each and show me the result):
1. Every log line parses as JSON.
2. One request id finds the web request and the background job it started.
3. Searching for user_id returns only that user's events.
4. A test that logs in and resets a password produces no secret in the logs.

If you skip it

Hours lost grepping text logs, no way to answer what happened to a customer's request, and secrets leaking into log storage.
