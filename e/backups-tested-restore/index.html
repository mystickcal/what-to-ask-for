Backups with a tested restore

Also called: database backup, pg_dump, restore drill, disaster recovery, point-in-time recovery

A backup only counts once you have restored it. Back up the database and uploaded files on a schedule, copy them off the server, and regularly restore into a throwaway database to prove they work.

You need it when

  • You store anything users would be upset to lose.

Skip it when

  • The data can be rebuilt from somewhere else.

Ways to build it

  1. pg_dump on a schedule, shipped off the server with restic $0 software plus storage

    A nightly pg_dump and an archive of uploads, encrypted and deduplicated by restic into object storage.

    Tradeoff: Simple. You lose whatever changed since the last dump.

  2. Continuous WAL archiving $0 software

    pgBackRest (or similar) for point-in-time recovery.

    Tradeoff: More setup. Worth it when losing hours of data is not acceptable.

  3. Managed database backups monthly cost

    A managed Postgres such as DigitalOcean's takes automated backups.

    Tradeoff: Less to run, but you still have to test a restore, and uploaded files need their own backup. A server snapshot is not the same as a tested database restore.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add backups with an automated restore test for [Postgres database + uploads folder].

Requirements:
- Nightly job: pg_dump in custom format plus an archive of uploaded files, taken together so they match.
- Encrypt and copy off the server to [bucket]. Keep [7 daily and 4 weekly].
- Write a manifest per run with file checksums.
- Restore test job: start a disposable Postgres, restore the latest backup into it, run a migrations check and a few row-count queries, then delete it. Record pass or fail.
- Refuse to run the restore test against anything that isn't the disposable database.
- Alert if the last good backup is older than [26 hours] or the last passing restore test is older than [8 days].
- Before each deploy, take a backup and stop the deploy if it fails.

Acceptance checks (run each and show me the result):
1. Restoring last night's backup into a scratch database shows a row created yesterday.
2. Pointing the restore test at the production database URL makes it refuse to run.
3. Backup files can't be read without the key.
4. Turning off the backup job triggers the stale-backup alert.
5. A deploy with a failed backup stops before migrations run.

If you skip it

You find out the backups were empty or unreadable on the day you need them.

How Derek runs it

Custody Journal's release runbook makes a matched database and media backup a hard gate before any release. Its encrypted manifest has to pass a restore into a disposable PostgreSQL container, and an attest command records that result. The app's operations health report flags a failed or uncommitted latest backup. There is also a command for copying backups off the server.
