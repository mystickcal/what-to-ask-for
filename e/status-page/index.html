Status page

Also called: system status, incident page, outage page, service status, incident communication

A public page, hosted away from your app, that shows whether each part of your service is working and lists incidents and planned maintenance with updates. It answers "is it just me?" without a support email.

You need it when

  • Paying customers rely on your app being up.
  • Every outage brings a pile of "is it down?" messages.

Skip it when

  • Very early, with few users. A pinned post or banner may do.

Ways to build it

  1. A hosted status page with monitoring free tiers, then paid

    Better Stack, Instatus, UptimeRobot and Atlassian Statuspage pair checks with a public page and subscriber emails.

    Tradeoff: Runs when your servers don't. Free tiers limit monitors and branding.

  2. Self-hosted $0 plus a small server

    Uptime Kuma or Gatus on a separate machine from your app, with its status page turned on.

    Tradeoff: Free and flexible. If it shares a host or network with your app, it goes down with it.

  3. A static page built by scheduled checks $0

    Upptime runs checks with GitHub Actions and publishes a status page on GitHub Pages.

    Tradeoff: No server at all. Checks run every few minutes at best.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Set up a public status page for my app with [tool].

Requirements:
- Host it on a different provider than the app, at [status.mydomain.com].
- Components: [website, API, background jobs, email]. Each backed by a real check (HTTP health endpoint, job heartbeat).
- Incidents: an investigating, identified, monitoring, resolved flow with timestamps. Prepare 3 short templates in plain words.
- Planned maintenance posts with start and end times in UTC and the reader's local time.
- Let users subscribe by email or RSS.
- Link it from the app footer, the help page and error pages.
- Write down who posts updates and how fast (for example within 15 minutes of an alert).

Acceptance checks (run each and show me the result):
1. Stopping the app server turns the website component red within a few minutes.
2. The status page stays up while the app is down.
3. A test incident reaches email subscribers.
4. The app's error page links to the status page.
5. Maintenance times show correctly in two timezones.

If you skip it

During an outage, users flood support and social media because there's nowhere to check, and trust drops more than the outage deserved.

People describe this as

  • “tell users the site is down before they email me”
  • “post updates during an outage”
  • “customers want to see our uptime history”
  • “announce planned maintenance”
