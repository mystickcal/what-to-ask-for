N+1 query fixes

Also called: N+1 queries, eager loading, select_related, too many database queries, query batching

A common ORM slowdown: one query loads a list, then one more query runs for each item to fetch related data. Load the related data in one or two queries up front (eager loading or batching) instead.

You need it when

  • List pages, feeds, exports and APIs that show related data for each row.

Skip it when

  • Pages with a single record and few relations.

Ways to build it

  1. Eager loading in the ORM $0

    Django select_related and prefetch_related, Rails includes, Prisma include, SQLAlchemy selectinload, Laravel with().

    Tradeoff: Usually a one-line fix per query. Over-eager loading pulls data you don't use.

  2. Batching with DataLoader $0

    Collect ids during a request and load them in one query, common with GraphQL resolvers.

    Tradeoff: Fixes it at the resolver level. More code to wire up.

  3. Detect it automatically $0

    Bullet (Rails), nplusone or django-debug-toolbar, Prisma query logs, and tests that assert query counts.

    Tradeoff: Catches new N+1s early. Tests need maintenance as pages change.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Find and fix N+1 queries in my app.

Requirements:
- Turn on query logging in development and list the [10] pages and API endpoints with the most queries per request.
- For each, show the repeated query and fix it with [eager loading / batching].
- Load only the columns and relations the page uses.
- Add a test per fixed endpoint that asserts the query count stays flat when the number of items grows (for example 5 items and 50 items give the same count).
- Add an N+1 detector in development that warns or fails tests.
- Report before and after query counts and response times.

Acceptance checks (run each and show me the result):
1. A list with 50 items runs the same number of queries as one with 5.
2. Query-count tests fail if someone removes the eager loading.
3. The slowest list page is noticeably faster.
4. No page loads large related data it doesn't show.
5. The detector flags a new N+1 in development.

If you skip it

Pages that were fast with test data crawl with real data, and the database gets busy doing tiny repeated queries.

People describe this as

  • “my list page runs hundreds of database queries”
  • “the page gets slower as I add more items”
  • “the ORM makes a query for every row”
  • “GraphQL resolvers are slow”
