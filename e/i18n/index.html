Translations and localization (i18n)

Also called: internationalization, localization, l10n, multi-language support, translate my app

Pulling every user-facing string out of the code into translation files, picking a language per user, and formatting dates, numbers, currencies and plurals with the locale's rules. Done early, it's cheap. Done late, it means touching every screen.

You need it when

  • You have or want users who prefer another language.
  • You show dates, numbers or money to people in more than one country.

Skip it when

  • One market, one language, no plans to change. Still use locale-aware date and number formatting.

Ways to build it

  1. Your framework's i18n system $0

    Django gettext with .po files, Rails I18n, i18next or next-intl for React, vue-i18n, Flutter intl.

    Tradeoff: Standard and free. You manage translation files and missing keys.

  2. A translation management platform free tiers, then paid

    Crowdin, Lokalise, Phrase, or open source Weblate or Tolgee sync files with your repo and give translators an editor.

    Tradeoff: Smooth for many languages and translators. Another tool to run or pay for.

  3. Machine translation first, review after API costs

    Translate new strings with an AI or translation API, then have a fluent speaker review key screens.

    Tradeoff: Fast. Legal, billing and safety text needs human review.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add translations to my app, starting with [Spanish].

Requirements:
- Use [framework i18n tool]. Move every user-facing string (pages, emails, errors, notifications) into translation keys.
- Whole sentences per key with placeholders, never sentences glued from pieces. Handle plurals with the library's plural rules.
- Language choice order: user setting, then the browser's Accept-Language, then [English]. Save the choice on the account and use it for emails too.
- Format dates, numbers and money with the locale (Intl API or framework helpers). Keep storing data in UTC and plain numbers.
- Set the html lang attribute. Make layouts survive 30 percent longer text.
- Add a check that fails CI on missing keys in any language file.
- Don't translate user-generated content.

Acceptance checks (run each and show me the result):
1. Switching to Spanish changes pages, emails and error messages.
2. 1 item and 2 items use the right plural forms.
3. Dates show as 21/10/2026 for es-ES and 10/21/2026 for en-US.
4. Removing a key from the Spanish file fails CI.
5. No English strings remain on main screens in Spanish mode.

If you skip it

Half-translated screens, broken grammar from glued strings, and a painful rewrite when the first non-English customer arrives.
