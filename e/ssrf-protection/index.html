SSRF protection

Also called: server-side request forgery, URL fetch allowlist, private IP blocking, outbound request guard

Guarding any feature where your server fetches a URL that a user supplied. Without it, someone can point your server at internal addresses, like a cloud metadata endpoint or an admin panel on localhost, and read the response through your app.

You need it when

  • Link previews, 'import from URL', user-set webhook URLs, PDF or screenshot rendering of user URLs, or an AI tool that browses.

Skip it when

  • Your server only calls fixed URLs that you wrote in the code.

Ways to build it

  1. Resolve, check, then connect to that IP $0

    Allow only https, resolve the host, reject any private, loopback, link-local or reserved address, then connect to the checked IP so a second DNS answer can't swap it. Don't follow redirects, or check each hop the same way.

    Tradeoff: Strong. Easy to get subtly wrong, so use a tested helper and test it.

  2. An outbound proxy with rules $0 self-hosted

    Send user-URL fetches through a proxy like Smokescreen that blocks internal ranges, and give the app no other route out for those calls.

    Tradeoff: One choke point for every feature. Another service to run.

  3. An allowlist of domains $0

    Only fetch from a known list, like the image hosts or integrations you support.

    Tradeoff: Safest. Too narrow for general link previews.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add SSRF protection to every place this app fetches a user-supplied URL ([features]).

Requirements:
- One shared fetch helper. All user-URL fetches go through it.
- Allow only https (http only in local development). Reject URLs with a username or password in them.
- Resolve the hostname with a time limit, and reject if any resolved address is private, loopback, link-local (including 169.254.169.254), multicast or reserved, for both IPv4 and IPv6.
- Connect to the IP you checked, not the hostname again, to block DNS rebinding.
- Don't follow redirects, or re-run every check on each redirect target with a limit of [3].
- Set a total timeout of [10] seconds and a response size cap of [1 MB].
- Never return raw error details or the internal response to the user.

Acceptance checks (run each and show me the result):
1. http://127.0.0.1, http://localhost and http://169.254.169.254/latest/meta-data/ are all rejected.
2. A hostname that resolves to 10.0.0.5 is rejected.
3. A public URL that redirects to an internal address is rejected.
4. IPv6 forms like http://[::1]/ are rejected.
5. A slow server is cut off at the timeout, and a huge response at the size cap.

If you skip it

Attackers read cloud credentials from the metadata service, reach internal admin tools, or scan your private network through your app.

How Derek runs it

Custody Journal's outgoing webhooks go through an SSRF guard. It requires https (http only in debug), rejects URLs with embedded credentials, resolves the host with a 5 second limit, and refuses if any resolved address isn't a public one. It then connects to the checked IP, never follows redirects, and caps each call at 10 seconds and a 64 KB response.

From the Custody Journal code and release runbook, read 2026-10-21.
