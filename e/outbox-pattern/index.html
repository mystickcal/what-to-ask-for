Transactional outbox

Also called: outbox pattern, reliable events, dual write problem, event publishing, transactional messaging

Instead of saving a record and then sending a message (two steps that can half fail), you save the record and an outbox row in one database transaction. A separate worker reads the outbox and sends the messages, retrying until each one is done.

You need it when

  • A database change must reliably trigger an email, webhook, queue message or call to another service.
  • You have seen "saved but never notified" bugs after crashes or deploys.

Skip it when

  • The side effect is fine to lose now and then, like a non-critical analytics ping.

Ways to build it

  1. Outbox table plus a polling worker $0

    An outbox table (id, type, payload, created, sent_at, attempts). The worker selects unsent rows with FOR UPDATE SKIP LOCKED, sends, marks sent.

    Tradeoff: Works with any SQL database and is easy to inspect. A few seconds of delay from polling.

  2. A Postgres-backed job queue $0

    Enqueue the job inside the same transaction with pg-boss (Node), Oban (Elixir), Procrastinate (Python) or River (Go), since the queue lives in your database.

    Tradeoff: The queue is the outbox, so no extra table. Your database carries the job load.

  3. Change data capture $0 software, more ops

    Debezium reads the database log and publishes outbox rows to Kafka or another broker.

    Tradeoff: Near real time at large scale. Heavy to run for a small app.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add a transactional outbox so database changes reliably trigger [emails / webhooks / queue messages].

Requirements:
- Create an outbox table: id, event type, payload JSON, created_at, available_at, attempts, sent_at, last_error.
- Wherever the code saves a change and then sends something, write the outbox row in the same transaction instead of sending inline.
- A worker claims due rows with SELECT ... FOR UPDATE SKIP LOCKED, sends them, and marks them sent.
- Retry failures with backoff and stop after [N] attempts, leaving the row for review.
- Give each event a unique id and send it along, so receivers can ignore duplicates.
- Delete sent rows older than [7 days].
- List every place in the code that still sends directly after a save.

Acceptance checks (run each and show me the result):
1. Killing the app right after the save still sends the message once it restarts.
2. If the transaction rolls back, nothing is sent.
3. Two workers running at once never send the same row twice in normal operation.
4. A broken receiver leaves rows with growing attempt counts, not lost messages.
5. Every send-after-save in the codebase goes through the outbox.

If you skip it

Orders exist with no confirmation email, or customers get emails for orders that never saved.

How Derek runs it

Custody Journal saves each outgoing webhook as a delivery row, unique on endpoint, event and a dedupe key, and a separate webhook worker leases due rows and sends them.
