Rate limiting

Also called: throttling, request limits, brute-force protection, 429 Too Many Requests

Count requests per key (IP address, user or API key) in a time window and refuse with 429 once the count passes the limit.

You need it when

  • Login, signup, password reset and one-time codes.
  • Any endpoint that costs you money per call: LLMs, email, SMS.
  • Public forms.

Skip it when

  • Static pages served from a CDN.

Ways to build it

  1. Rules at the edge free plan available

    Cloudflare WAF rate limiting rules block by IP before traffic reaches your server.

    Tradeoff: Stops floods cheaply, but only sees IPs and paths, not your logged-in users or plans.

  2. Counters in your app, stored in Redis $0

    Fixed or sliding window counters in Redis or your shared cache. Libraries: django-ratelimit, express-rate-limit with a Redis store.

    Tradeoff: Can key on user id and plan. In-memory counters reset on restart and aren't shared between processes, so use Redis.

  3. Usage quotas in the database $0

    Count generations per user per month in a table and check it before the expensive call.

    Tradeoff: Right for paid limits. It is billing logic, so it needs tests.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add rate limiting to [endpoints].

Requirements:
- Use a shared store (Redis) so limits hold across processes and restarts.
- Limits: [login: 5 tries per 15 minutes per IP and per account], [AI endpoint: N per hour per user].
- Get the client IP correctly behind our proxy. Only trust X-Forwarded-For when the request comes from our proxy, and take the address our proxy added (counted from the right), not the leftmost one.
- Return 429 with a Retry-After header and a plain message.
- For login, reset and code entry, fail closed: if the counter store is down, refuse the attempt.

Acceptance checks (run each and show me the result):
1. The 6th login attempt inside 15 minutes returns 429.
2. Sending a made-up X-Forwarded-For header doesn't reset the limit.
3. Limits still apply after restarting the app.
4. With Redis stopped, login refuses attempts instead of allowing unlimited tries.
5. Normal use (browsing, one login) never sees a 429.

If you skip it

Password guessing, scraped content, and a surprise bill when a bot finds your AI endpoint.

How Derek runs it

Custody Journal uses fixed-window counters in the Redis cache it already runs, with no extra library, and hashes the counter keys. Security-sensitive limits fail closed: if the counter store is unavailable, the request is denied. The client IP comes from X-Forwarded-For only when the request arrives from a trusted proxy, counted from the right by the number of proxy hops, so a spoofed header can't dodge the limit.
