Pagination

Also called: paging, cursor pagination, keyset pagination, infinite scroll, load more, offset limit

Returning a list a page at a time instead of all at once. Offset paging (page 3 of 20) is simple and fine for small lists. Cursor paging (give me the 25 after this one) stays fast on big tables and doesn't skip or repeat items when rows are added while someone scrolls.

You need it when

  • Any list or API that can grow past a few hundred rows.

Skip it when

  • Lists with a hard small cap, like a user's 5 saved addresses.

Ways to build it

  1. Offset and limit $0

    LIMIT 25 OFFSET 50, or your framework's paginator. Shows page numbers and a total.

    Tradeoff: Easy. Deep pages get slow on big tables, and rows shift when new ones arrive.

  2. Cursor (keyset) pagination $0

    Sort by a unique, indexed key like (created_at, id) and return a cursor for the last row. The next page asks for rows after it.

    Tradeoff: Fast at any depth and stable while data changes. No jumping to page 37.

  3. Search engine paging varies

    If the list comes from a search service, use its own paging and result limits.

    Tradeoff: Fits search results. Totals are often estimates.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add pagination to [list page / API endpoint].

Requirements:
- Use cursor pagination ordered by (created_at, id) descending, with an index that matches that order. The response includes items and next_cursor (null on the last page).
- Page size defaults to [25] and the client can't ask for more than [100].
- The cursor is opaque to the client (base64-encoded) and is validated on input.
- Keep the user's filters and ownership check on every page.
- In the UI, add a 'Load more' button (or infinite scroll that also has a button for keyboard users).
- If page numbers are required, use offset paging only for this small list and say why.

Acceptance checks (run each and show me the result):
1. The first request returns 25 items and a next_cursor.
2. Following cursors to the end returns every item exactly once, even if new items are added during the walk.
3. Asking for 10,000 items returns at most 100.
4. EXPLAIN shows the query uses the index on deep pages.
5. A tampered cursor returns 400, not a server error.

If you skip it

List pages that time out as data grows, APIs that return a million rows, and feeds that repeat or skip items.
