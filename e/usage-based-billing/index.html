Usage-based billing

Also called: metered billing, billing meters, pay as you go, prepaid credits, credit balance, overage charges

Charging for how much someone used instead of a flat fee. Your app records each billable event in its own database first, then reports totals to the billing system, which adds them to the invoice. Prepaid credits are the other common shape: the user buys a balance and each use draws it down.

You need it when

  • Your costs grow with use, like AI tokens, SMS or compute, and a flat price would lose money on heavy users.

Skip it when

  • Usage is small or predictable. A flat plan with a hard limit is simpler to build and to explain.

Ways to build it

  1. Stripe billing meters Stripe fees

    Create a meter, attach a usage-based price, and send meter events with a customer id, a value and an identifier. Stripe enforces uniqueness of the identifier within a rolling period of at least 24 hours, which guards against double counting on retries.

    Tradeoff: Invoicing is handled for you. You still need your own usage records to show users their usage and to reconcile.

  2. Prepaid credits in your database $0 plus normal payments

    Sell credit packs through Checkout. Keep a credit ledger table with one row per purchase or use, and check the balance inside a transaction before the expensive call.

    Tradeoff: Simple to understand and no surprise bills. Refunds and expiring credits need care.

  3. Open-source metering and billing $0 software

    Lago can be self-hosted to take in usage events, add them up and produce invoices, with a payment provider underneath.

    Tradeoff: You own the data and logic. Another system to run and keep in sync.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add usage-based billing for [billable action] using [Stripe meters / prepaid credits].

Requirements:
- Write one usage row per billable action in our database: account id, quantity, unique event id, created time. The event id is unique so a retry can't count twice.
- [Meters] A job sends unsent usage rows to Stripe as meter events with our event id as the identifier, marks them sent, and retries failures.
- [Credits] Keep a ledger table (purchases positive, uses negative). Check and deduct the balance in one transaction with a row lock before the action runs. Refuse with a clear message at zero.
- Show users their usage or balance for the current period on the billing page.
- Add a daily reconcile job that compares our totals with the billing provider and reports any difference.

Acceptance checks (run each and show me the result):
1. Running the same billable action twice with the same event id records it once.
2. Ten parallel requests with a balance of 5 credits run exactly 5 actions.
3. The usage on the billing page matches what the provider shows for the same period.
4. Turning off the send job for an hour, then back on, sends every missed event once.
5. A user at zero credits gets a clear message and the expensive call is never made.

If you skip it

Heavy users cost more than they pay, retries bill people twice, and nobody can explain an invoice.

People describe this as

  • “charge per AI generation”
  • “bill customers for what they used this month”
  • “sell credits that get used up”
  • “a plan that includes 1,000 calls and charges for extra”
  • “count API calls for billing”
