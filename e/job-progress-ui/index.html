Job status and progress UI

Also called: progress bar, job status page, task status polling, long running task UI, processing status

A record for each long job (queued, running, percent, done or failed, result link) plus a screen that reads it. The page asks for updates every few seconds or listens for them, survives a refresh, and shows a real error when the job fails.

You need it when

  • Any background job a user waits for: exports, imports, AI generation, video or file processing.

Skip it when

  • The work finishes in under a couple of seconds. A plain loading state is enough.

Ways to build it

  1. Status row plus polling $0

    A jobs table the worker updates, and a GET /jobs/:id endpoint the page polls every 2 to 5 seconds, slowing down over time.

    Tradeoff: Simple and robust behind any proxy. Updates arrive a few seconds late.

  2. Server-sent events or websockets $0 to low

    Push status changes to the page as they happen over SSE or a websocket (or a hosted service like Pusher or Ably).

    Tradeoff: Instant updates. More moving parts, and you still need the status row for refreshes.

  3. Your queue's built-in job state $0

    BullMQ job progress, Celery task state or Inngest run status, exposed through your own endpoint.

    Tradeoff: Less code. Queue state usually expires, so keep your own record for anything users come back to.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add a job status and progress screen for [long task].

Requirements:
- A jobs table: id, owner, type, status (queued, running, succeeded, failed, canceled), progress 0 to 100, message, result URL, error code, created, started, finished.
- The worker updates progress at real milestones (rows processed, pages rendered), not a fake timer.
- GET /jobs/:id returns the row to its owner only. Poll every 2 seconds, backing off to 10, and stop when finished.
- The page survives refresh and works from a link in a notification email.
- On failure, show a plain error and a retry button. Never leave a spinner running.
- Mark jobs stuck in running past [timeout] as failed.
- Let users cancel a queued or running job where the work allows it.

Acceptance checks (run each and show me the result):
1. Refreshing mid-job shows the same job and progress.
2. Another user gets 404 for the job URL.
3. A job that throws shows the failed state and retry button within one poll.
4. A worker crash leaves the job marked failed after the timeout, not running forever.
5. Polling stops once the job finishes.

If you skip it

Users start the same export five times, or wait on a spinner for a job that died an hour ago.

People describe this as

  • “show a progress bar while the export runs”
  • “users refresh the page and lose track of their job”
  • “tell the user when the video is done processing”
  • “the spinner never stops after an error”
