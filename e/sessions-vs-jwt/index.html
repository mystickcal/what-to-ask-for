Sessions vs JWT

Also called: session cookie, JSON Web Token, access token, refresh token, stateless auth, bearer token

Two ways to remember who is logged in. A session is a random id in a cookie that points to data on your server, so you can end it any time. A JWT is a signed token that carries the user's details itself, so the server doesn't look anything up, but it stays valid until it expires unless you add a revocation list.

You need it when

  • Every app with logins makes this choice, often without noticing.

Skip it when

  • Your auth provider already decides it. Learn which one it uses and how logout works.

Ways to build it

  1. Server-side sessions in a cookie $0

    Your framework's sessions, stored in the database or Redis. Cookie flags: HttpOnly, Secure, SameSite=Lax.

    Tradeoff: Simple and easy to revoke. The usual right answer for a web app on one domain.

  2. Short-lived JWT plus a refresh token $0

    An access token valid for minutes and a refresh token that is rotated on each use and stored server-side so it can be revoked.

    Tradeoff: Fits APIs used by many services. More moving parts, and logout only takes effect when the access token expires.

  3. Opaque tokens stored hashed $0

    For mobile apps and API keys: a random token sent as a bearer header, stored as a hash, and checked against the database on each request.

    Tradeoff: Revocable like sessions and no cookies needed. One lookup per request.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Set up login state for this app using [server-side sessions / short-lived JWT plus refresh token].

Requirements:
- Web: session cookie with HttpOnly, Secure and SameSite=Lax. Don't put tokens in localStorage.
- Sessions expire after [30 minutes idle / 14 days absolute] and on logout.
- A 'log out of all devices' button ends every session or refresh token for the user.
- Changing the password or email ends other sessions.
- [JWT] Access tokens expire in [10 minutes]. Refresh tokens are random, stored hashed, rotated on every use, and reuse of an old refresh token revokes the whole family.
- Rotate the session id at login.

Acceptance checks (run each and show me the result):
1. document.cookie in the browser console doesn't show the session cookie.
2. After 'log out of all devices', a second browser that was logged in is logged out on its next request.
3. A copied session cookie stops working after logout.
4. [JWT] Using an old refresh token a second time fails and logs out that device.
5. The session id changes after login.

If you skip it

Logout doesn't really log anyone out, and a stolen token works until it expires.

How Derek runs it

Custody Journal's website uses server-side Django sessions (the cached_db engine), with secure cookies in production, a 30 minute idle timeout by default, and expiry when the browser closes. Its mobile app uses opaque access and refresh tokens that are stored as hashes and can be revoked. There is no JWT signing.
