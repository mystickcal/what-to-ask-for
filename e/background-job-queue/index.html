Background job queue

Also called: task queue, worker, async job, background worker, job runner

The web request saves a job and answers right away. A separate worker picks up the job, does the slow part and stores the result. The page checks back for it.

You need it when

  • A step takes more than a few seconds: LLM calls, video or image work, PDFs, big exports.
  • A step calls an outside service that can fail and should be retried.

Skip it when

  • The work is fast and you need the answer before you can reply to the user.

Ways to build it

  1. A jobs table in the database you already have $0

    Workers claim rows with a lock (Postgres FOR UPDATE SKIP LOCKED). Libraries: pg-boss (Node), River (Go), good_job (Rails), or a small model in Django.

    Tradeoff: No new service to run. Fine for modest volume. Polling adds a little database load.

  2. A Redis-backed queue $0 if you run Redis

    Celery or RQ for Python, BullMQ for Node.

    Tradeoff: Fast and common, but it is one more service to run and monitor, and Redis persistence settings decide whether queued jobs survive a restart.

  3. A hosted background job service free tiers

    Inngest or Trigger.dev run steps for you and call back into your code.

    Tradeoff: Less to operate. Another account, your data leaves your server, and moving off it later is work.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Move [slow task] out of the web request into a background job.

Requirements:
- On request: validate input, create a job row (status pending, dedupe key, owner), and return 202 with the job id within 500 ms.
- A worker claims jobs with a lease (token plus claimed_at). If a worker dies, the job becomes claimable again after the lease expires.
- Retry with backoff up to [3] attempts, then mark it failed with a short error code. No stack traces or user data in that field.
- Add a status endpoint that returns pending, running, done or failed, plus the result link when done. Only the owner can read it.
- Cap active jobs per user and in total. Return 429 or 503 with a plain message when full.
- The page polls the status endpoint every [2] seconds and shows progress.

Acceptance checks (run each and show me the result):
1. The request returns in under 500 ms even when the task takes 60 seconds.
2. Killing the worker in the middle of a job and restarting it finishes the job exactly once.
3. Submitting the same request twice quickly creates one job.
4. A task that always fails ends as failed after the max attempts and the page says so.
5. Changing the job id in the URL can't show another user's job.

If you skip it

Requests time out behind your proxy, users click again and start duplicate work, and one slow call ties up the whole server.

How Derek runs it

Custody Journal runs exports as queued jobs stored in Postgres. Each job has a dedupe key, a lease token and a max attempt count. Jobs with expired leases go back into the queue, or fail after the last attempt. There are caps on active exports per user and in total: a user with an export already running gets a 429, and a full queue returns 503.
