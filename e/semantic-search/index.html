Semantic search and RAG

Also called: vector search, embeddings, pgvector, retrieval augmented generation, RAG, chat with your docs

Turning text into embeddings (lists of numbers that capture meaning) so you can find passages similar to a question even when the words differ. RAG feeds the best passages to a model so it answers from your content instead of guessing.

You need it when

  • Users ask questions in their own words, or an AI feature must answer from your documents.

Skip it when

  • Users search for names, codes or exact phrases. Full-text search does that better and cheaper.

Ways to build it

  1. pgvector in Postgres $0

    Store chunk embeddings in a vector column with an HNSW index next to your data, and filter by owner in the same query.

    Tradeoff: One database, normal permissions and backups. Tuning is up to you at large scale.

  2. Hybrid search $0

    Run full-text and vector search together and merge the results (for example reciprocal rank fusion). Meilisearch and Typesense support hybrid search too.

    Tradeoff: Catches both exact terms and meaning. A bit more logic to maintain.

  3. A managed vector database paid, free tiers

    Pinecone, Qdrant Cloud or Weaviate Cloud, or your AI provider's file search tool.

    Tradeoff: Scales without tuning. Another copy of your data to keep in sync and secure.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add semantic search (and answers from it) over [documents] in this app.

Requirements:
- Split documents into chunks of about [500] tokens with some overlap, keeping the title and section heading with each chunk.
- Create embeddings with [embedding model] in a background job on create and update. Store them with pgvector and an HNSW index, plus the owner or tenant id.
- Every search query filters by the current user's access before ranking.
- Combine vector and full-text results, and return the top [5] chunks with links to their source.
- For answers, send only those chunks to the model, tell it to answer only from them and say when it doesn't know, and show the sources.
- Re-embed when a document changes and delete chunks when it's deleted.
- Build a test set of 20 questions with known source documents and report how often the right source is in the top 5.

Acceptance checks (run each and show me the result):
1. A question using different words from the document still finds it.
2. User B's question never retrieves user A's chunks.
3. Deleting a document removes it from results and answers.
4. Answers cite their sources, and a question with no answer in the docs gets 'I don't know'.
5. The right source is in the top 5 for at least [18 of 20] test questions.

If you skip it

Answers made up from nowhere, results from other users' documents, and stale answers from deleted files.

People describe this as

  • “find documents by meaning, not exact words”
  • “let users chat with their own documents”
  • “the AI should answer from my help articles”
