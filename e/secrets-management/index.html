Secrets management

Also called: environment variables, API key storage, .env file, secret rotation, leaked API key

Keeping API keys, passwords and signing keys out of your code, your git history and the browser. They live in your host's secret settings or a secrets manager, the app reads them at startup, and you know how to replace each one quickly if it leaks.

You need it when

  • Your app talks to any paid API, database or payment provider. That's almost every app.

Skip it when

  • Never.

Ways to build it

  1. Host environment variables $0

    Set secrets in Vercel, Netlify, Render, Fly or your server's env, keep .env in .gitignore, and commit a .env.example with names only.

    Tradeoff: Enough for most apps. Copies spread across environments and people's laptops.

  2. A secrets manager $0 self-hosted, paid tiers

    Infisical (open source), Doppler, 1Password Secrets Automation, or your cloud's secret manager inject secrets at deploy time.

    Tradeoff: One place to rotate and audit. Another service your deploys depend on.

  3. Leak prevention $0

    Turn on GitHub secret scanning and push protection, and run gitleaks in a pre-commit hook or CI.

    Tradeoff: Catches mistakes before they ship. Doesn't help with a key that's already public: that one must be rotated.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Clean up how this app handles secrets.

Requirements:
- Find every secret in the code, config files and git history (run gitleaks or a similar scanner). List them by name only. Never print a value.
- Move each to environment variables read at startup. Add a .env.example with the names and no values, and make sure .env is in .gitignore.
- Make sure no secret reaches the browser: check client bundles and any NEXT_PUBLIC_, VITE_ or similar prefixed variables. Calls that need a secret key go through the server.
- The app fails to start in production if a required secret is missing, and the error names the variable, not its value.
- For any secret found in git history, write the rotation steps (create a new key, deploy, revoke the old one). Removing it from history is not enough.
- Turn on secret scanning and push protection for the repo.

Acceptance checks (run each and show me the result):
1. gitleaks reports no secrets in the working tree.
2. Searching the built frontend bundle finds no secret key prefixes (like sk_live_ or sk-).
3. Starting the app without a required secret fails with a message naming it.
4. Logs and error pages never show a secret value.

If you skip it

Leaked keys get found and used fast: surprise AI bills, stolen data and abused payment accounts.

How Derek runs it

Custody Journal refuses to start in production without a SECRET_KEY. A check script validates each service's environment before deploy, fails closed, and reports only variable names and the service role, never values. Key files must be absolute paths with mode 0400 or 0600, and backup encryption keys have IDs so older keys can still decrypt after a rotation.
