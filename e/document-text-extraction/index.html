Text from PDFs and scans

Also called: OCR, PDF parsing, document parsing, PDF text extraction, read invoices, document AI

Turning uploaded files into text your app or an AI model can use. PDFs made on a computer have a text layer you can read directly. Scans and photos are only images, so they need OCR or a model that can read images. Either way the work should run with limits, because files from users can be huge, broken or hostile.

You need it when

  • Users upload documents and expect the app or the AI to understand them.
  • You want to pull out fields like dates, totals or names.
  • Some uploads are scans or phone photos.

Skip it when

  • You only store files and show them back. Nobody needs the text.

Ways to build it

  1. Read the text layer $0

    pypdf or pdfplumber for PDFs and the document XML for Word files.

    Tradeoff: Fast, free and exact. Gets nothing from scans, and tables come out jumbled.

  2. OCR $0 with Tesseract, or paid per page with cloud OCR

    Run Tesseract yourself, or send pages to AWS Textract or Google Document AI, which also find tables and form fields.

    Tradeoff: Reads scans. Makes mistakes on bad photos, and cloud OCR means the document leaves your servers.

  3. Send the file to a vision model Paid per page or token

    OpenAI and Anthropic models accept PDFs and images directly. Ask for structured output with the fields you need.

    Tradeoff: Handles messy layouts and pulls out fields in one step. Costs more, can misread, and the file goes to the provider.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add text extraction for uploaded documents.

Requirements:
- Support [PDF, DOCX, TXT, JPG, PNG]. Check the real file type, not just the extension.
- For PDFs, read the text layer first. If a page has no text, [send it to OCR with Tesseract / send it to our vision model / tell the user it looks like a scan].
- Run extraction in a background job or a separate process with a time limit, a memory limit and a size limit. Stop at [50] pages or [12,000] characters and say when the text was cut off.
- Refuse encrypted PDFs and broken files with a plain message. Never put document text in error logs.
- Never change the original file. Store the extracted text separately with the page count and method used.
- If I ask for fields, return them as JSON that matches a schema, and keep the raw text so a person can check it.

Acceptance checks (run each and show me the result):
1. Upload a normal PDF, a scanned PDF, a phone photo of a page and a Word file. Each one gives readable text or a clear message.
2. A scanned PDF with no text layer is either sent to OCR or refused with a message that says why. It never comes back as empty text with no warning.
3. A 300 page PDF stops at the page or size limit and says the text was cut off.
4. An encrypted or broken file is refused without crashing the worker, and the error log has no document text in it.

If you skip it

Your AI quietly answers from empty text when someone uploads a scan, and one huge or booby trapped PDF can tie up a worker or crash your app.

How Derek runs it

Custody Journal reads attachments for its AI assistant in a separate worker process with memory and CPU limits and a time limit of at most 8 seconds. It reads PDFs, Word files, plain text and CSV, takes up to 50 pages of a PDF with pypdf, keeps the first 12,000 characters and marks the text as cut off, and refuses encrypted PDFs. Images are shrunk to 2048 pixels and sent to the model as images. Its agreement compare tool tells users a scanned PDF may need OCR first.
