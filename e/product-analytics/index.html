Product analytics events

Also called: event tracking, funnel tracking, PostHog, Umami events, conversion tracking, activation metrics

Sending a small named event when a user does something that matters, like signing up, finishing setup or upgrading, so you can count each step and see where people stop. Page views tell you traffic. Events tell you whether the product is working.

You need it when

  • You want to know how many visitors sign up, activate and pay.
  • You are deciding what to build next and want usage, not guesses.

Skip it when

  • You have a handful of users you can just talk to. A few queries on your own database may answer the question.

Ways to build it

  1. Privacy-friendly page analytics with custom events $0 self-hosted, paid hosted

    Umami or Plausible, with a few custom events on the buttons and forms that matter.

    Tradeoff: Light, cookieless and easy. Basic funnels only.

  2. A product analytics tool Free tier

    PostHog or Mixpanel, with server-side events for signups and payments and a user id that is not an email.

    Tradeoff: Real funnels, retention and cohorts. More setup and more privacy work.

  3. Your own events table $0

    Write a row per important event to your database and query it.

    Tradeoff: You own the data and it never leaves. You build the charts yourself.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add product analytics events for this funnel: [landing view, signup, first key action, upgrade, paid].

Requirements:
- Write down an event list first: snake_case names, when each fires, and its properties. Keep it under [10] events.
- Send signup and payment events from the server, after the database write succeeds, so ad blockers and refreshes don't change the counts.
- Use an id that is not personal, like a hash of the user id. Never send emails, names, or text the user typed.
- Respect the existing consent setting. If consent is declined, send nothing to third parties.
- Make each event fire once per real action, not once per page render or retry.
- Use [Umami / Plausible / PostHog / an events table] and put the tracking calls in one small helper module.

Acceptance checks (run each and show me the result):
1. Signing up in staging creates exactly one sign_up event with the agreed properties.
2. A funnel from landing page view to paid shows a count for every step.
3. No event payload contains an email, name or free text the user typed.
4. With analytics consent declined, the network tab shows no requests to the analytics provider.

If you skip it

You guess where users get stuck, ship features nobody uses, and can't tell whether a change helped. Tracked carelessly, you leak personal data into a third party.

How Derek runs it

Custody Journal saves a fixed list of funnel events, from signup intent through subscription started, to its own database. It sends events to PostHog only for signed-out visitors on the home, start and pricing pages after they accept analytics, and uses a hashed id instead of the account id or email.
