Caching and invalidation

Also called: Redis cache, cache invalidation, memoization, stale data, TTL, cache stampede

Keeping the result of slow or costly work for a while so the next request can reuse it. The hard parts are the key (it must include everything the result depends on, including the user) and knowing when the saved copy is out of date.

You need it when

  • The same expensive query, API call or AI call runs again and again with the same inputs.

Skip it when

  • The page is already fast. Fix slow queries with indexes before adding a cache.

Ways to build it

  1. Content-addressed keys with a TTL $0

    Build the key from a hash of every input (model name, prompt, settings, user id where relevant) and set an expiry. New inputs make a new key, so nothing needs deleting.

    Tradeoff: No invalidation bugs. Only works when the result depends only on the inputs in the key.

  2. Redis or Valkey with delete on write $0 self-hosted

    Cache reads in Redis or Valkey and delete the key in the same code path that saves the data.

    Tradeoff: Fresh data after saves. Every write path must remember to delete, and you need a plan for when the cache is down.

  3. HTTP caching $0

    Cache-Control and ETag headers so browsers and CDNs reuse public responses.

    Tradeoff: Cheapest of all. Only safe for responses that are the same for everyone, or marked private.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add caching for [slow operation] in this app.

Requirements:
- First measure: log how long the operation takes and how often it runs with the same inputs. Show me the numbers.
- Cache in [Redis/Valkey, or the framework cache]. Build each key from a prefix, a version and a hash of every input the result depends on. Include the user or tenant id for anything user-specific.
- Set a TTL of [X]. For data users edit, delete the key in the same code path that saves it.
- If the cache is unreachable, fall back to doing the work (fail open) and log a warning without the key or values. Security features such as rate limits must not fall back this way.
- Prevent a stampede: only one request rebuilds an expired key while others wait briefly or get the old value.
- Never cache responses with private data in a shared or CDN cache.

Acceptance checks (run each and show me the result):
1. The second identical request is at least [5x] faster, shown with timings.
2. After a user edits the data, the next read shows the new value.
3. User A never receives a cached result that belongs to user B.
4. Stopping Redis keeps the app working, just slower.
5. 100 parallel requests for an expired key run the expensive work once.

If you skip it

Stale pages after saves, users seeing each other's data, an app that dies when the cache does, and AI bills for repeat work.

How Derek runs it

Custody Journal uses Redis as one cache shared by all workers when it's configured, and falls back to per-process memory otherwise. AI tone results are cached for 7 days under a SHA-256 of the model, the input and a flag, so a new input or model simply makes a new key. Its optional cache helpers fail open and log a warning without the key, because keys can contain session ids.
