Storing money amounts

Also called: currency handling, integer cents, decimal money, rounding money, multi-currency

Keeping money exact. Store amounts as whole minor units (cents) in an integer column, or as a fixed DECIMAL, always next to a currency code. Never use floating point for money, and round once, at a defined step.

You need it when

  • Your app shows, adds up or charges any price, fee, balance or split.

Skip it when

  • Never. Even one price field benefits from getting this right on day one.

Ways to build it

  1. Integer minor units $0

    amount_cents BIGINT plus currency CHAR(3), the same shape Stripe's API uses. Convert to display format only at the edge.

    Tradeoff: Exact and fast. Currencies with 0 or 3 decimals need a lookup table.

  2. DECIMAL columns and decimal types $0

    NUMERIC(12,2) in the database and Python Decimal, Java BigDecimal or a library like dinero.js in code.

    Tradeoff: Readable values. Every language boundary (JSON, JavaScript) must avoid floats.

  3. A money library $0

    dinero.js (JavaScript), py-moneyed or django-money (Python), the money gem (Ruby) bundle amount and currency with safe math.

    Tradeoff: Fewer mistakes. One more dependency.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Fix how my app stores and calculates money.

Requirements:
- Find every money field and every place money is calculated.
- Store amounts as [integer minor units in a BIGINT] with a currency code column (ISO 4217). No float or double anywhere.
- Do math in integers or a decimal type. Round once, with a named rule ([half up / banker's]), at a defined step such as per line item.
- When splitting amounts (for example 100 into 3), give the leftover cent to a defined party so parts always add up to the total.
- Send amounts in APIs as integers with currency, never as floats.
- Format for display with the user's locale only in the UI.
- Write a migration that converts existing data exactly, and tests for rounding and splits.

Acceptance checks (run each and show me the result):
1. Searching the schema and code finds no float columns or float math on money.
2. Splitting $100.00 three ways gives parts that add to exactly $100.00.
3. A yen price has no decimals and a dollar price has two.
4. Totals match the payment provider's to the cent across 1,000 test orders.
5. JSON responses carry integers, not 19.990000000001.

If you skip it

Invoices and payouts drift by cents, reports never reconcile with the payment provider, and support gets "you overcharged me" emails.

People describe this as

  • “my totals are off by a cent”
  • “0.1 plus 0.2 doesn't equal 0.3 in my invoice”
  • “store prices in different currencies”
  • “how should I save prices in the database”
