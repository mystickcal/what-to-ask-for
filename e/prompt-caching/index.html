Prompt caching

Also called: prompt cache, cached input tokens, context caching, KV cache discount

A provider feature that reuses the processed start of a prompt when the next request begins with exactly the same text. Repeated instructions, documents and chat history cost less and return faster. Put the parts that never change first and the changing parts last.

You need it when

  • Requests share a long fixed beginning, like a big system prompt, examples, a document or the earlier turns of a chat.

Skip it when

  • Prompts are short or different every time. Caching only applies above a minimum length.

Ways to build it

  1. Automatic caching (OpenAI) discount

    On current OpenAI models, prompts of 1,024 tokens or more are cached automatically. Keep the shared prefix identical and check cached_tokens in the usage data.

    Tradeoff: No code change beyond ordering. Any change early in the prompt breaks the cache.

  2. Explicit cache breakpoints (Anthropic) discount on reads

    Mark the end of the reusable part with cache_control. Cache writes cost more than normal input (1.25x for the 5 minute cache, 2x for 1 hour) and reads cost about a tenth.

    Tradeoff: You control what's cached and for how long. Pays off only if the prefix is reused before it expires.

  3. Cache whole answers yourself $0

    For identical requests, store the final answer under a hash of the model and full input.

    Tradeoff: Free and instant. Only helps exact repeats.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Use prompt caching to cut cost and latency in [AI feature] on [provider].

Requirements:
- Reorder each prompt so fixed content comes first (system instructions, tool definitions, examples, shared documents) and per-request content comes last (user input, dates, ids).
- Remove anything that changes on every request from the fixed part, such as timestamps or random ids.
- [Anthropic] Add cache_control at the end of the fixed part. [OpenAI] Make sure the fixed part is at least 1,024 tokens or caching won't apply.
- Log cached and uncached input tokens from the usage data on every call.
- Compare cost and time to first token for 50 requests before and after.

Acceptance checks (run each and show me the result):
1. From the second request on, usage shows cached input tokens.
2. The fixed part of the prompt is byte-for-byte identical between requests.
3. Average cost per request drops, shown with the before and after numbers.
4. Answers are unchanged on the eval set.

If you skip it

Paying full price thousands of times for the same instructions, and slow first tokens on long chats.

People describe this as

  • “every request sends the same long instructions and I pay for them each time”
  • “my chatbot gets slower and more expensive as the chat grows”
  • “cut the cost of a long system prompt”
