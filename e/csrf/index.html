CSRF protection

Also called: cross-site request forgery, CSRF token, SameSite cookies, XSRF

Stopping other websites from making a logged-in user's browser send state-changing requests to your app. It matters when login lives in cookies, because the browser attaches them automatically. APIs that only accept a token in the Authorization header aren't exposed in the same way.

You need it when

  • Your app uses cookie sessions and has forms or endpoints that change data.

Skip it when

  • The API accepts only bearer tokens in a header and never reads a cookie for auth.

Ways to build it

  1. Your framework's built-in protection $0

    Django's CsrfViewMiddleware, Rails' protect_from_forgery, or Laravel's CSRF middleware. Next.js server actions compare the Origin and Host headers by default, but your own route handlers need their own check.

    Tradeoff: Proven. Exemptions added to silence errors are where the holes appear.

  2. SameSite cookies plus Origin checks $0

    Set session cookies to SameSite=Lax or Strict and reject state-changing requests whose Origin header isn't yours.

    Tradeoff: Strong defence in modern browsers. Best used together with tokens, not instead of them.

  3. Header-only token auth $0

    Keep the auth token out of cookies and send it in the Authorization header from your own code.

    Tradeoff: Not exposed to CSRF. The token then has to be kept away from cross-site scripting.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Audit and fix CSRF protection in this app.

Requirements:
- Confirm the framework's CSRF protection is on for every route that changes data (POST, PUT, PATCH, DELETE).
- List every CSRF exemption with the reason. Keep an exemption only if the endpoint authenticates another way (a webhook signature, or a bearer token with cookies refused).
- No GET request changes data. Move any that do to POST.
- Session cookies use Secure, HttpOnly and SameSite=Lax (or Strict).
- Set the trusted origins list for production domains only.
- Add a test that posts a form without the token and expects 403.

Acceptance checks (run each and show me the result):
1. A form posted from another origin without a token is rejected.
2. Every CSRF exemption is listed with how that endpoint authenticates instead.
3. Grep shows no GET handler that writes to the database.
4. The session cookie shows Secure, HttpOnly and SameSite in the browser's dev tools.

If you skip it

A malicious page can change a user's email, delete data or make purchases using the user's own logged-in browser.

How Derek runs it

Custody Journal keeps Django's CSRF middleware on for the whole site, and production trusted origins default to the site's own https domains. The exemptions are the Stripe webhook (checked by signature), a small anonymous analytics endpoint, OAuth endpoints for an integration, and mobile API endpoints that refuse cookie sessions and accept only bearer tokens. Sign-in links use a POST confirm step, so a GET never logs anyone in.
