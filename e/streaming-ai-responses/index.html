Streaming AI responses

Also called: token streaming, server-sent events, SSE, typewriter effect, stream the answer

Sending the model's answer to the browser piece by piece as it's generated, usually over server-sent events, so people see text within a second instead of waiting for the whole reply. Your server sits in the middle, keeps the API key private, and saves the finished answer.

You need it when

  • Chat or writing features where answers take more than a couple of seconds.

Skip it when

  • The output is structured data your code uses, or the work runs in a background job. Stream progress, not tokens, there.

Ways to build it

  1. Server-sent events from your backend $0

    Call the provider with streaming on, and forward each text chunk to the browser as an SSE event. The browser reads it with fetch and a stream reader, or EventSource for GET requests.

    Tradeoff: Works with any backend. Proxies and hosts can buffer the stream unless you turn that off.

  2. An AI SDK $0

    The Vercel AI SDK or the provider's own SDK helpers handle the streaming protocol and the UI state for you.

    Tradeoff: Least code. Ties your frontend to the SDK's message format.

  3. Stream progress from a background job $0

    For long tasks, run the AI call in a job and push status updates over SSE or polling.

    Tradeoff: Survives page reloads and timeouts. Text appears in bigger steps.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Stream AI responses to the browser in [feature].

Requirements:
- The browser calls our server, never the provider directly. The API key stays on the server.
- Use the provider's streaming mode and forward text chunks as server-sent events (Content-Type: text/event-stream, Cache-Control: no-cache).
- Turn off response buffering in every proxy in front of the app (for nginx, X-Accel-Buffering: no) and check the host's streaming limits and timeouts.
- If the user closes the page or presses Stop, cancel the upstream request so we stop paying for tokens.
- Save the full answer and token usage to the database when the stream ends, including partial answers when cancelled.
- Show a clear message, not a stack trace, if the stream fails halfway.

Acceptance checks (run each and show me the result):
1. In production, the first words appear within [2] seconds of sending.
2. Pressing Stop ends the provider request (visible in server logs) within a second.
3. Reloading the page shows the saved answer.
4. The API key never appears in browser network requests.
5. Killing the connection mid-answer shows a friendly error and keeps the partial text.

If you skip it

Users think the app froze, streams that work locally arrive in one lump in production, and you pay for answers nobody is reading.

People describe this as

  • “show the AI answer as it's being written”
  • “users stare at a spinner while the model thinks”
  • “my streamed response arrives all at once in production”
