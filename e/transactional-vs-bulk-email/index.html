Transactional vs bulk email

Also called: transactional email, marketing email, newsletter sending, message streams, email outbox

Transactional email is one message to one person because of something they did: a sign-in link, a receipt, a reset. Bulk email is the same message to many people: newsletters, announcements. Send them through separate streams or providers so complaints about one don't hurt delivery of the other, and send from a background job, not inside the web request.

You need it when

  • Your app sends both kinds, or plans to.

Skip it when

  • You send only a few transactional emails and no marketing at all.

Ways to build it

  1. One provider with separate streams free or cheap tiers

    Postmark message streams, or separate configuration sets and subdomains in Amazon SES, keep the two kinds of mail apart.

    Tradeoff: One account to manage. Some providers don't allow marketing mail on the transactional stream at all.

  2. A transactional provider plus a newsletter tool $0 software for self-hosted lists

    Postmark, Resend or SES for app mail. Listmonk (self-hosted) or a hosted newsletter tool for lists.

    Tradeoff: Each tool does its own job well. Two places to keep unsubscribes in sync.

  3. A database outbox for app mail $0

    Save the email as a row in the same transaction as the change that caused it. A worker sends it and retries.

    Tradeoff: Mail is never lost, and never sent for a change that was rolled back. You run the worker.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Split our email into transactional and bulk.

Requirements:
- Transactional mail (sign-in, reset, receipts, alerts) goes through [provider/stream A] from [mail.example.com].
- Bulk mail (newsletters, announcements) goes through [provider/stream B] from [news.example.com], with List-Unsubscribe headers.
- Never send from inside the web request. Save an outbox row in the same transaction and let a worker send it with retries.
- Transactional mail doesn't need an unsubscribe link, but it must not carry marketing content.
- In development, all mail goes to Mailpit.
- Log message id, type and status. Never log full bodies with personal data.

Acceptance checks (run each and show me the result):
1. Signing up returns quickly even when the email provider is slow or down.
2. Stopping the worker, signing up, then starting it again delivers the email once.
3. A newsletter test send shows the bulk subdomain and a List-Unsubscribe header.
4. Password reset emails still arrive during a newsletter send.
5. No email is sent for a change that was rolled back.

If you skip it

A spike in newsletter complaints sends your password resets to spam, and a slow email API slows down signups.

How Derek runs it

Custody Journal sends sign-in email through its own database outbox. The outbox row is created in the same transaction as the sign-in token, and the recipient, subject and body are stored encrypted. Onboarding tips and the weekly digest are separate email types, each with its own unsubscribe link, and a code comment notes that trial reminders go through the transactional backend because marketing providers don't own billing mail.
