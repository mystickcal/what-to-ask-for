Audit log

Also called: activity log, change history, audit trail, who changed what

An append-only record of important actions: who did what to which record, when, and from where, with the values before and after. It answers support questions and security reviews, and some customers require it.

You need it when

  • Several people can edit the same data, or admins can act on user accounts.
  • Customers ask for compliance features or you handle sensitive records.

Skip it when

  • A single-user app with no admin tools, where ordinary logs are enough.

Ways to build it

  1. An audit table you write to $0

    A table with actor, action, target type and id, before and after values, IP and time. Write to it in the same transaction as the change.

    Tradeoff: Full control over what's recorded. You have to call it from every place that matters.

  2. A history library $0

    django-simple-history, PaperTrail (Rails), or Postgres triggers that copy old rows into a history table.

    Tradeoff: Captures every model change automatically. Doesn't capture who unless you pass the user in, and stores a lot.

  3. An audit log service paid

    Hosted audit log products like WorkOS Audit Logs, often used when enterprise customers ask for exports.

    Tradeoff: Exports and customer-facing views built in. Another vendor holding sensitive data.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add an audit log for [models/actions].

Requirements:
- Record actor (user id or 'system'), action (create, update, delete, plus named actions like role_changed), target type and id, changed fields with before and after values, IP, user agent and UTC time.
- Write the audit row in the same transaction as the change, so neither can exist without the other.
- Never store passwords, tokens, API keys or full card data. Mask or hash sensitive fields.
- The audit table is append-only for the app: no update or delete code paths, and no edit form in admin.
- Add a page where [admins / the account owner] can filter the log by user, record and date.
- Keep entries for [1 year], then delete them with a scheduled job.

Acceptance checks (run each and show me the result):
1. Editing a record creates one audit row with the right before and after values.
2. A failed edit that rolls back leaves no audit row.
3. No secret or token appears anywhere in the audit table.
4. The app has no route that edits or deletes audit rows.
5. The filter page finds all changes to one record.

If you skip it

No way to answer 'who did this', disputes you can't settle, and failed security reviews. A log that stores secrets becomes a leak of its own.

How Derek runs it

Custody Journal logs create, update and delete for six models (entries, communications, custody events, children, documents and reports) when the change comes from a signed-in request. Each row keeps the previous and current data, IP, user agent and session key. Encrypted fields are stored as an HMAC fingerprint, so the log shows that a field changed without holding the text.
