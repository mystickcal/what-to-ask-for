Live updates (WebSockets, SSE or polling)

Also called: websockets, server-sent events, real-time updates, live data, pub/sub, presence

Getting changes to the browser as they happen. Polling asks every few seconds. Server-sent events stream one way from server to browser. WebSockets go both ways. Pick the simplest one that meets the delay users will notice.

You need it when

  • Chat, collaborative editing, live dashboards, notifications, or anything where a stale screen causes mistakes.

Skip it when

  • Updates every 30 seconds are fine. Polling is enough and much simpler.

Ways to build it

  1. Polling $0

    Fetch an endpoint every few seconds, ideally with If-Modified-Since or a since cursor.

    Tradeoff: Works everywhere, nothing new to run. Some delay and wasted requests.

  2. Server-sent events $0

    A long-lived HTTP response that streams events, with automatic reconnect in the browser's EventSource.

    Tradeoff: Simple for server-to-browser updates. Proxies need buffering off and long timeouts.

  3. WebSockets, self-run $0 plus server capacity

    Socket.IO, Django Channels, Phoenix Channels or Rails Action Cable, with Redis for fan-out across servers.

    Tradeoff: Two-way and fast. Sticky connections, scaling and auth are your job.

  4. A hosted realtime service free tiers, then paid

    Pusher, Ably, Supabase Realtime, Liveblocks or PartyKit carry the connections. Your server publishes events.

    Tradeoff: No connection servers to run. Per-connection or per-message pricing.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add live updates for [feature] using [polling / SSE / WebSockets / hosted service].

Requirements:
- Explain the choice in two sentences based on how fresh the data must be and whether the browser sends data back.
- Authenticate the connection with the user's session or a short-lived token. Subscribe only to channels the user may see, checked on the server.
- Send small events (type, id, changed fields) and let the client fetch full data if needed.
- On reconnect, catch up from the last event id or timestamp so nothing is missed.
- Fall back to polling if the connection fails repeatedly.
- Configure the proxy for long-lived connections (timeouts, buffering off for SSE).
- With more than one server, fan out through [Redis pub/sub / the hosted service].

Acceptance checks (run each and show me the result):
1. A change made in one browser shows up in another within [2] seconds.
2. A user can't subscribe to another user's channel by changing its name.
3. Dropping the network for 30 seconds, then reconnecting, shows missed updates.
4. Two app servers both deliver events to their connected users.
5. Polling fallback works when WebSockets are blocked.

If you skip it

Users see stale data and overwrite each other, or private updates go to the wrong browser.

People describe this as

  • “show new messages without refreshing”
  • “update the dashboard live”
  • “should I use websockets or polling”
  • “show who else is viewing the document”
