Staging environment

Also called: staging server, preview deployments, test environment, pre-production

A second copy of your app that runs the same code and setup as production but with its own database, keys and test-mode payments. You deploy there first, click through the change, and then promote the same build to production.

You need it when

  • Real users depend on the app and changes touch payments, auth, data or migrations.

Skip it when

  • Very early, when preview deploys per pull request cover what you need.

Ways to build it

  1. Preview deployments $0, included

    Vercel, Netlify, Render and others build each branch or pull request at its own URL. Point them at a separate preview database or a seeded branch database (Neon and Supabase have branching).

    Tradeoff: Almost no setup. Sharing the production database by accident is the main risk.

  2. A staging stack on your own server $0 + server

    The same Docker Compose setup in its own directory, with its own Postgres, Redis and secrets, behind basic auth and a noindex header.

    Tradeoff: Matches production closely. Uses server resources and needs its own care.

  3. A separate staging project at your host paid, usually

    A second app or project with test-mode Stripe keys, a sandbox email provider and its own domain.

    Tradeoff: Closest to production. Costs another set of resources.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Set up a staging environment for this app on [host].

Requirements:
- Staging runs the same build and config shape as production, with its own database, cache, storage bucket and secrets. Nothing in staging can reach production data.
- Use Stripe test-mode keys, a sandbox or capture-only email setup, and fake or seeded data. No copies of real user data unless they're anonymized.
- Protect staging with a password (basic auth or the host's protection) and send X-Robots-Tag: noindex.
- Deploy to staging only from committed code on [main], then promote that same build to production.
- Show a visible 'STAGING' banner in the UI.
- Write the steps for deploying to staging and promoting to production.

Acceptance checks (run each and show me the result):
1. Staging's database URL, keys and bucket differ from production's.
2. A test payment in staging uses test mode and never touches live Stripe.
3. Opening staging without the password is refused.
4. Search engines get a noindex header from staging.
5. The promoted production build is the same commit that was tested.

If you skip it

Changes get tested on real users, test emails reach customers, or staging writes into the production database.

How Derek runs it

Custody Journal has a staging stack with its own Postgres and Redis containers, behind basic auth and a noindex header. Its deploy script ships the committed state of origin/main, never the local working tree.
