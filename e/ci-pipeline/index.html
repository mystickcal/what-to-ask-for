CI checks on every push

Also called: continuous integration, GitHub Actions, CI pipeline, pre-merge checks, release gate

An automatic run of your tests, linters, type checks and build on every push or pull request. A red result blocks the merge or deploy, so a change that breaks something is caught in minutes instead of by users.

You need it when

  • You have any tests, or you ship code written by AI agents and want a safety net.

Skip it when

  • Never once there's a second contributor, human or AI.

Ways to build it

  1. GitHub Actions free for public repos, monthly free minutes for private

    A workflow file runs on push and pull_request: install, lint, type check, test, build. Mark it required in branch protection.

    Tradeoff: Built into GitHub. Private repo minutes run out on heavy suites.

  2. Your host's or Git provider's CI free tiers

    GitLab CI, Bitbucket Pipelines, CircleCI, or build checks on Vercel, Netlify and Render.

    Tradeoff: Fine choices. Pick the one next to your code.

  3. A local release script $0

    One script you (and your agents) run before each deploy that runs every check and refuses to continue on failure.

    Tradeoff: Free and fast on your machine. Only works if it can't be skipped.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Set up CI that runs on every push and pull request.

Requirements:
- Steps in order: install from lockfile, lint, type check, unit tests, migrations check ([no missing migrations]), build, then [a short end-to-end smoke test].
- Use a real database service of the same version as production for tests, not SQLite if production is Postgres.
- Cache dependencies. Target under [10] minutes.
- Add a dependency audit step that fails on high severity.
- Make the workflow required for merging into main.
- Fail on warnings that hide real bugs (unawaited promises, unused imports) once the code is clean.
- Show me how to run the exact same checks locally with one command.

Acceptance checks (run each and show me the result):
1. A pull request with a failing test can't be merged.
2. The local command and CI run the same steps.
3. A model change without a migration fails CI.
4. CI runs against the same database engine as production.
5. A typical run finishes in under 10 minutes.

If you skip it

Bugs that tests would have caught reach production, and nobody knows which change caused them.

How Derek runs it

Custody Journal uses a free local release gate script rather than hosted CI. It runs ruff, Django checks, a missing-migrations check, a migration cycle test, the full test suite, pip-audit, npm audit, a Postgres concurrency test, a Playwright smoke test and a Docker build, and it fails closed.
