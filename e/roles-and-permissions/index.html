Roles and permissions

Also called: RBAC, role-based access control, authorization, admin role, access control, permission checks

Rules for who may do what. Users get a role (owner, admin, member, viewer) and each action checks the role on the server. Hiding a button only changes what people see. The server must refuse the request too.

You need it when

  • More than one kind of user: staff, admins, team members, read-only guests.

Skip it when

  • Every user only ever sees and edits their own data. Ownership checks cover that.

Ways to build it

  1. A role column and one permission helper $0

    Store the role on the membership row and write one function, can(user, action, thing), that every view and API calls. Deny by default.

    Tradeoff: Enough for most apps. Gets messy if rules depend on many conditions.

  2. A permissions library $0

    django-rules, CASL (JavaScript) or Pundit (Rails) keep named rules in one place, usable in code and templates.

    Tradeoff: Cleaner rules. One more concept for your agent to learn.

  3. A policy engine $0 software or paid

    OpenFGA (open source, relationship-based) or a hosted service works out permissions outside your app.

    Tradeoff: Good for complex sharing like Google Docs. Overkill for a few roles.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add roles and permissions: [owner, admin, member, viewer].

Requirements:
- Store the role on the membership between a user and [team/workspace].
- Write one function can(user, action, object) with a table of which role may do which action. Deny anything not listed.
- Call it on the server in every view and API route that reads or changes data. The UI can use the same function to hide buttons, but the server check is the protection.
- Only owners can change roles, and the last owner can't be removed or demoted.
- Log role changes with who, whom, old role, new role and time.
- Add a test per role per action from the table.

Acceptance checks (run each and show me the result):
1. A viewer who sends the edit request directly (curl or devtools) gets 403.
2. An admin can't promote themselves to owner.
3. Removing the last owner is refused.
4. Every route in the app is covered by a permission check (list any that aren't).
5. The test suite has a passing test for each role and action pair.

If you skip it

Any logged-in user can reach admin actions by guessing the URL.

People describe this as

  • “admins can do more than regular users”
  • “let some team members view but not edit”
  • “a normal user found the admin page”
  • “hide the delete button for viewers”
