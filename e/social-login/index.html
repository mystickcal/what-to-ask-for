Social login (OAuth and OpenID Connect)

Also called: Sign in with Google, OAuth login, OpenID Connect, OIDC, SSO, PKCE

Users sign in with an account they already have. Your app sends them to the provider, gets back a code, and swaps it on the server for tokens that say who they are. Use a library for this, keep the requested permissions small, and only link to an existing account when the provider says the email is verified.

You need it when

  • You want sign-up with no password and less friction.
  • Your users are businesses that expect Google or Microsoft sign-in.

Skip it when

  • Your users don't have, or don't want to use, those accounts. Offer email sign-in too.

Ways to build it

  1. An auth library in your framework $0

    django-allauth, Auth.js or Better Auth. They handle the code flow, state, PKCE and account linking.

    Tradeoff: Your data stays in your database. You still register an app with each provider and set exact redirect URLs.

  2. A hosted auth service free tiers

    Clerk, Auth0, Supabase Auth or Firebase Auth add many providers from a dashboard.

    Tradeoff: Fastest. Your user list lives with them and pricing grows with users.

  3. A self-hosted identity provider $0 software

    Keycloak, Authentik or Zitadel run on your server and speak OpenID Connect to your apps.

    Tradeoff: Good when several apps share one login. Heavy to run for a single app.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add [Google] sign-in using [library].

Requirements:
- Use the authorization code flow with PKCE and a state parameter. No implicit flow.
- Ask only for openid, email and profile. Ask for other permissions later, when a feature needs them.
- Register exact redirect URIs for each environment. No wildcards.
- If the email matches an existing account, link them only when the provider marks the email as verified. Otherwise refuse and explain.
- Keep the provider's client secret in an environment variable.
- Show a friendly error page when the user cancels or the provider fails, and log the provider's error code.

Acceptance checks (run each and show me the result):
1. A new Google user who signs in twice still has one account.
2. An existing email user who signs in with Google (verified email) lands in their existing account, not a new one.
3. A callback with a wrong or missing state value is rejected.
4. The consent screen asks only for basic profile and email.
5. Canceling on the provider's screen shows our error page, not a stack trace.

If you skip it

Duplicate accounts, account takeover through an unverified email, or a consent screen asking for far more than you need.

How Derek runs it

Custody Journal uses django-allauth with Google as the only social provider. PKCE is on, sign-in asks only for profile and email, and calendar access is requested separately inside the app. The Google prompt is set to select_account so the wrong browser account isn't reused. A verified Google email can sign in to an existing account with the same email.
