Structured output from LLMs

Also called: JSON mode, structured outputs, function calling, tool use, JSON schema output

Getting the model to return data in a fixed shape your code can rely on. Use the provider's schema feature where it exists, then validate the result anyway and decide what happens when it doesn't fit: retry once, fall back, or show an error.

You need it when

  • Your code reads fields out of the model's answer: labels, extracted data, decisions or tool arguments.

Skip it when

  • The output is only text shown to a person.

Ways to build it

  1. Provider schema enforcement $0

    OpenAI Structured Outputs with a strict JSON schema, or tool definitions with an input schema (OpenAI function calling, Anthropic tool use), using strict mode where the provider offers it.

    Tradeoff: The provider holds the shape in strict mode. Supported schema features are limited, and the model can still refuse or pick wrong values.

  2. JSON mode plus your own validation $0

    Ask for JSON, parse it, and validate with Pydantic or Zod. JSON mode only promises valid JSON, not your schema.

    Tradeoff: Works across more models. You handle mismatches yourself.

  3. A library $0

    Instructor (Python) or the Vercel AI SDK's object generation take a Pydantic or Zod schema and handle retries.

    Tradeoff: Less glue code. One more dependency to keep current.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Make [AI feature] return structured data.

Requirements:
- Define the output schema in [Pydantic/Zod]: field types, required fields, enums for fixed choices, max lengths.
- Use the provider's structured output or tool schema feature with that schema where supported.
- Validate every response against the schema in our code, even when the provider enforces it. Check enum values against our allowed list.
- On invalid output or a refusal, retry once, then fall back to [safe default / non-AI path] and log the failure.
- Never pass model output straight into SQL, shell commands, file paths or HTML.
- Add tests with real sample inputs, plus a mocked malformed response.

Acceptance checks (run each and show me the result):
1. 100 sample inputs all produce output that passes validation, or are handled by the fallback.
2. A mocked response with an unknown enum value is rejected.
3. A mocked malformed response triggers one retry and then the fallback.
4. The schema in the code and the one sent to the provider come from one definition.

If you skip it

Features that crash on the one response in fifty that isn't valid JSON, or code that acts on made-up field values.

How Derek runs it

Custody Journal's tone classifier asks the model for a JSON object, then checks that the label is one of three allowed values and keeps only hits in known categories. Anything that doesn't fit falls back to the keyword classifier.
