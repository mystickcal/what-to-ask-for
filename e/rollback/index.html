Rollback plan

Also called: roll back a deploy, revert release, instant rollback, previous version, blue-green deploy

A tested way to put the last working version back in minutes. Keep the previous build around, know which database changes it can live with, and practice the switch before you need it.

You need it when

  • Anyone uses the app while you deploy.

Skip it when

  • Never. Even if it's one command, write it down and try it once.

Ways to build it

  1. Your host's instant rollback $0, included

    Vercel, Netlify, Render, Fly and Railway keep earlier deployments and can switch traffic back to one.

    Tradeoff: Seconds to roll back code. Doesn't undo database migrations.

  2. Tagged images and a scripted switch $0

    Tag each Docker image with the commit, record what's live before a release, and have a script restart the app on the previous image and wait for health checks.

    Tradeoff: Works on any server. You maintain the script and must test it.

  3. Blue-green or canary deploys $0 + capacity

    Run the new version beside the old one and move traffic over, all at once or a slice at a time, with a quick switch back.

    Tradeoff: Smoothest. Needs a load balancer and double capacity during the switch.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Give this app a tested rollback plan for [host/server].

Requirements:
- Every release is an immutable build (image or deployment) tagged with its commit.
- Before a release, record what's live: the build id, config and environment.
- One command or button rolls back to the previous build and waits until health checks pass.
- Database migrations follow expand and contract, so the previous build still runs on the new schema. Rolling back never reverses a migration automatically.
- If health checks fail after a release, roll back automatically and alert me.
- Write a one-page runbook and do a practice rollback on staging.

Acceptance checks (run each and show me the result):
1. A practice rollback on staging finishes in under [5] minutes with health checks green.
2. After a rollback, the app runs on the previous build against the current database.
3. A deliberately broken release triggers the automatic rollback.
4. The runbook says exactly which command to run and how to confirm it worked.

If you skip it

A bad release stays live while you debug under pressure, or a hurried rollback breaks the database.

How Derek runs it

Before each release, Custody Journal's release script records the live Compose setup, runtime config and previous image. If anything fails, a trap rolls back automatically: it restarts the six app services on the previous image and waits until they're healthy. The database and Redis containers are left alone, and migrations are never reversed, so a preflight check first proves the previous image runs on the new schema.
