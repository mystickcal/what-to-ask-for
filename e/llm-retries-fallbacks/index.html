LLM retries, timeouts and fallbacks

Also called: AI API errors, 429 rate limit from OpenAI, overloaded error, model fallback, exponential backoff

Treating the model API like any network service that will sometimes be slow or fail. Set timeouts, retry only the errors worth retrying with backoff, and decide what users see when it's still failing: a cheaper model, a simpler non-AI result, or a clear message.

You need it when

  • Any feature that calls a model API in a user's request or in a job.

Skip it when

  • Never. Even a demo should have a timeout.

Ways to build it

  1. SDK settings plus your own rules $0

    Set the SDK's timeout and max_retries explicitly (the OpenAI Python SDK retries 2 times by default). Retry 429, 5xx and overloaded errors with exponential backoff and jitter, and honour any retry-after header.

    Tradeoff: Simple. Retries add waiting time inside a user's request, so keep the total budget small.

  2. A retry library $0

    tenacity (Python) or p-retry (Node) around the call, with a stop condition on total time.

    Tradeoff: Clear policy in one place. Make sure the SDK isn't also retrying underneath.

  3. Fallbacks through a gateway $0 self-hosted, paid tiers

    LiteLLM (open source) or a hosted gateway like OpenRouter routes to a second model or provider when the first fails.

    Tradeoff: Survives provider outages. Prompts and output can differ between models, so test the fallback.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Make the AI calls in [feature] reliable.

Requirements:
- Set an explicit timeout on every model call ([30] seconds for user requests). Set the SDK's max_retries explicitly so we know how many retries happen.
- Retry only rate limits (429), server errors (5xx) and overloaded errors, with exponential backoff and jitter, honouring retry-after. Never retry 400-level errors such as invalid requests or auth failures.
- Cap the total time including retries at [45] seconds for user-facing calls.
- If retries run out, fall back to [cheaper model / non-AI result / saved result], or show a plain message like 'The AI service is busy, try again in a minute'.
- Never show raw provider errors to users. Log the error type and request id.
- Long or batch work runs in a background job with its own retry policy.

Acceptance checks (run each and show me the result):
1. A mocked 429 is retried and then succeeds.
2. A mocked 400 is not retried.
3. A mocked hang is cut off at the timeout with a friendly message.
4. With the main provider forced to fail, the fallback runs, or users see the clear message.
5. No user ever sees a raw provider error or stack trace.

If you skip it

Pages that hang forever, features that die with every provider blip, and retry storms that make rate limits worse.

How Derek runs it

Custody Journal's assistant calls the provider with a 30 second timeout and no automatic retries, inside a child process with a deadline, and maps timeouts, rate limits and provider errors to plain messages. Its tone classifier uses a 20 second timeout and one retry, and falls back to a keyword classifier on any error.
