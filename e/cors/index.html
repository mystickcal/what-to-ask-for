CORS settings

Also called: cross-origin resource sharing, Access-Control-Allow-Origin, preflight, CORS error

Headers your API sends to tell browsers which other websites may read its responses. CORS only loosens the browser's same-origin rule. It doesn't stop scripts, servers or curl from calling your API, so it never replaces authentication.

You need it when

  • Your frontend and API are on different origins (domain, subdomain or port) and the browser blocks the call.

Skip it when

  • Frontend and API share one origin, for example the API lives at /api on the same domain. Then you need no CORS headers at all.

Ways to build it

  1. Serve both from one origin $0

    Route /api to the backend through your host's rewrites or a reverse proxy, so the browser sees one site.

    Tradeoff: No CORS to get wrong, and cookies just work. Needs a proxy or rewrite rule.

  2. Framework CORS middleware with an allowlist $0

    django-cors-headers, the cors package for Express, or FastAPI's CORSMiddleware, with an explicit list of allowed origins.

    Tradeoff: Standard. Easy to loosen to * during debugging and forget.

  3. CORS at the edge $0

    Set the headers in Nginx, Caddy or a Cloudflare rule in front of the API.

    Tradeoff: Works for any backend. Keeps rules away from the code that needs them.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Fix CORS for the API at [api origin] used by [frontend origins].

Requirements:
- Allow only these exact origins: [list], read from config per environment. No wildcard, and never reflect the request's Origin header back without checking it against the list.
- If the browser sends cookies, set Access-Control-Allow-Credentials: true. That requires a specific origin, never *.
- Allow only the methods and headers the frontend uses, and handle OPTIONS preflight requests.
- Add Vary: Origin when the response depends on the origin.
- Explain in a comment that CORS is not access control. Every endpoint still checks authentication.

Acceptance checks (run each and show me the result):
1. The real frontend can call the API with no CORS errors in the console.
2. A request with Origin: https://evil.example gets no Access-Control-Allow-Origin header.
3. curl -X OPTIONS with an allowed origin returns the expected allow headers.
4. No response anywhere has Access-Control-Allow-Origin: * together with credentials.

If you skip it

Either the frontend can't reach the API, or a wide-open setting lets any website read signed-in users' data through their browser.

People describe this as

  • “blocked by CORS policy error in the browser”
  • “my frontend on one domain can't call my API on another”
  • “is Access-Control-Allow-Origin star safe”
