Plan limits and entitlements

Also called: feature gating, entitlements, paywall, quota enforcement, free tier limits, usage limits per plan

One place in your code that answers "is this account allowed to do this, and how much is left?" based on its plan. Every feature asks it instead of checking plan names itself, and limit checks happen in the same transaction as the work they guard.

You need it when

  • You have a free tier, or more than one paid plan with different limits.

Skip it when

  • One plan, everything included.

Ways to build it

  1. An entitlements module in your code $0

    A map from plan to features and limits, plus functions like can(account, feature) and remaining(account, limit). Plan comes from your subscription records.

    Tradeoff: Simple and fast. Changing a plan means a deploy.

  2. Your payment provider's entitlements included or paid add-on

    Stripe Entitlements attach features to products and tell you which ones a customer has.

    Tradeoff: Plans live next to prices. You still enforce counts in your own code.

  3. A pricing and entitlements service free tiers, then paid

    Tools like Schematic, Stigg or Autumn manage plans, limits and metering and expose a check API.

    Tradeoff: Change plans without deploys. Another dependency in your request path.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add plan limits and feature entitlements to my app.

Requirements:
- One module defines each plan's features and limits: [free: 10 projects, no export; pro: unlimited, export].
- Functions: can(account, feature) and remaining(account, limit). No other code checks plan names.
- Read the plan from my subscription records (kept current by webhooks), with a safe default of free.
- Enforce on the server. Hide or disable locked buttons in the UI too, with an upgrade link.
- Check and create in one transaction with a row lock on the account, so two requests at once can't both pass the last slot.
- Count what users can't easily dodge, for example items created this month even if later deleted or archived.
- On downgrade, keep existing data readable and block only new creation past the limit.
- Tests for each plan and limit, including two requests at the same moment.

Acceptance checks (run each and show me the result):
1. A free user creating the 11th project gets a clear upgrade message from the API, not only the UI.
2. Firing 5 create requests at once at 9 used gives 10, not 14.
3. Deleting items doesn't reset a monthly cap if the rule says it shouldn't.
4. Downgrading keeps old data readable.
5. Searching the code for plan names finds them only in the entitlements module.

If you skip it

Free users get paid features through the API or a race, or paying users hit walls meant for the free tier.

How Derek runs it

Custody Journal keeps its free-tier entry cap in one quota module used by the journal, calendar and bulk import. It counts entries created this month whether or not they were later archived, skips auto-saved drafts, and runs the check and the creation inside one lock so two requests can't both take the last slot.

From the Custody Journal code and release runbook, read 2026-10-21.

  • “lock a feature behind the Pro plan”
  • “users get around the free tier limit”
  • “check what plan a user is on before running something”
