Uptime monitoring

Also called: uptime check, status page, downtime alerts, synthetic monitoring, heartbeat monitoring

An outside service that checks your site every minute or so and alerts you when it fails. Heartbeat checks do the reverse for jobs: the job pings the monitor when it finishes, and you're alerted when the ping doesn't arrive.

You need it when

  • Anyone besides you depends on the app being up.
  • You have scheduled jobs whose silent failure would hurt.

Skip it when

  • Never once you have users. It's cheap and quick to set up.

Ways to build it

  1. Uptime Kuma $0 self-hosted

    Run it on a different server from your app. HTTP, keyword and push (heartbeat) monitors, with alerts to email, Slack, Telegram and more.

    Tradeoff: Free and flexible. If it shares a server with your app, it goes down with it.

  2. Hosted uptime service free tiers

    UptimeRobot, Better Stack or similar check from several regions and host a status page.

    Tradeoff: Independent of your servers. Free tiers check less often.

  3. Heartbeats for jobs $0, free tiers

    Healthchecks.io (open source, or hosted with a free tier) gives each job a URL to ping when it succeeds.

    Tradeoff: Catches jobs that stop running, which uptime checks can't see.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Set up uptime and job monitoring for this app.

Requirements:
- Monitor [home page URL] and [readiness URL] every [1-5] minutes from outside my infrastructure. The readiness check should fail when the database is unreachable.
- Use a keyword check on a page so a blank or error page counts as down, not just a 200.
- Add a heartbeat ping at the end of each scheduled job ([list]), sent only on success, with a grace period that fits each schedule.
- Alert by [email/Slack/SMS] after [2] failed checks in a row, and alert again when it recovers.
- Optional: a public status page for the main site.
- Write down every monitor, what it checks and who gets the alert.

Acceptance checks (run each and show me the result):
1. Stopping the app triggers an alert within the expected time.
2. Breaking the database connection makes the readiness monitor fail.
3. Skipping one run of a scheduled job triggers its heartbeat alert.
4. The recovery alert arrives when things come back.

If you skip it

Outages and dead background jobs that you find out about from angry users, days later.

People describe this as

  • “tell me when my site is down”
  • “my site was down all weekend and I didn't know”
  • “alert me if the nightly job stops running”
  • “add a status page”
