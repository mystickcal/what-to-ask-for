Multi-tenant data isolation

Also called: tenant isolation, workspaces, organizations, row level security, RLS, tenant_id

Keeping each customer's data separate when they all share one app and one database. Every row carries a tenant id, every query filters on it, and a database rule such as Postgres row level security can act as a second lock in case code forgets.

You need it when

  • Customers are companies or teams, not single people.
  • Your frontend talks to the database directly, as with Supabase.

Skip it when

  • Each user only has their own data and nothing is shared. Ownership checks on each query are enough.

Ways to build it

  1. A tenant_id column and scoped queries $0

    Add tenant_id to every table, set the current tenant once per request, and use a base query or manager that always filters by it.

    Tradeoff: Simple and cheap. One unscoped query leaks data, so test it.

  2. Postgres row level security $0

    Turn on RLS for each table and write policies that compare tenant_id to the current user's tenant. On Supabase this is required for any table the browser can reach with the anon key.

    Tradeoff: The database enforces it. Table owners skip RLS unless you FORCE it, and roles with BYPASSRLS (like Supabase's service_role key) always skip it.

  3. A schema or database per tenant more ops

    django-tenants (schema per tenant), or a separate database for each big customer.

    Tradeoff: Strong separation. Migrations and reporting across tenants get harder.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add tenant isolation for [organizations/workspaces].

Requirements:
- Every table with customer data gets a non-null tenant_id with an index.
- Work out the current tenant once per request from the logged-in user's membership, never from a request parameter alone.
- All reads and writes go through a scoped query helper that filters by tenant_id. Search the codebase and list any query that bypasses it.
- [Postgres/Supabase] Enable row level security on these tables with policies that limit rows to the user's tenant. Never ship the service_role key to the browser.
- Background jobs carry the tenant id explicitly.
- Add tests that create two tenants and prove neither can read or change the other's rows through any API route.

Acceptance checks (run each and show me the result):
1. Logged in as tenant A, requesting tenant B's record id returns 404.
2. With the anon key, a direct select on each table returns no other tenant's rows.
3. Exports, search and reports for tenant A contain no tenant B data.
4. A background job for tenant A can't write to tenant B.
5. The browser bundle contains no service_role or admin key.

If you skip it

One customer sees another customer's data. For a B2B app that can end the business.

People describe this as

  • “one company can see another company's data”
  • “add teams or workspaces to my app”
  • “my Supabase tables are readable by anyone with the anon key”
  • “make sure every query only returns this customer's rows”
