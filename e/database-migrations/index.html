Safe database migrations

Also called: schema migrations, expand and contract, zero-downtime migration, migration rollback

Changing the database schema in small steps that the old and new versions of your code can both live with, checked in CI and run as a release step. Renames and drops happen in two releases: add the new shape, move the code and data, then remove the old shape.

You need it when

  • Your app has real data and you change models after launch.

Skip it when

  • Before launch with throwaway data, where resetting the database is fine.

Ways to build it

  1. Your framework's migrations, checked in CI $0

    Django migrations, Rails migrations, Alembic, Prisma Migrate or Drizzle Kit. CI fails if models changed without a migration (for example makemigrations --check) and runs all migrations on a fresh database.

    Tradeoff: Standard and enough for most apps. The tools don't stop slow or unsafe operations by themselves.

  2. A linter for unsafe migrations $0

    strong_migrations (Rails), django-migration-linter, or Squawk for raw Postgres SQL flag table locks, non-concurrent indexes and drops of columns still in use.

    Tradeoff: Catches the ones that cause outages. Adds a few rules to learn.

  3. Expand and contract by hand $0

    Release 1 adds the new column and writes to both. A backfill copies old rows. Release 2 reads the new column. Release 3 drops the old one.

    Tradeoff: No downtime for renames and type changes. Takes several releases.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Set up safe migrations for this app and plan the change to [describe schema change].

Requirements:
- CI fails if a model changed without a migration, and runs every migration on an empty database.
- Never edit a migration that has already run in production. Fix forward with a new one.
- Split renames, type changes and drops into expand and contract steps that work with both the old and new code during a deploy.
- Create indexes on large tables without locking writes (CREATE INDEX CONCURRENTLY on Postgres).
- Backfill large tables in batches in a background job, not inside the migration.
- Migrations run as one release step before the new code takes traffic, and a backup is taken first.
- Write down for each migration whether it can be reversed.

Acceptance checks (run each and show me the result):
1. CI fails when I change a model and skip the migration.
2. All migrations apply on a fresh database with no errors.
3. During the deploy, the old code keeps working against the new schema.
4. A test copy of production data migrates in a known time without long locks.
5. The plan lists which steps are reversible.

If you skip it

Deploys that take the app down, locked tables, columns dropped while old code still reads them, and migration histories that differ between machines.

How Derek runs it

Custody Journal has a migration check script that fails on conflicting or missing migrations, runs every migration forward on a throwaway SQLite database, runs a full rollback and forward cycle when every step is reversible, and proves that irreversible migrations stop a rollback. Its release runbook never reverses migrations: rolling back code is allowed only after a preflight check proves the previous version runs on the new schema.
