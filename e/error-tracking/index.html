Error tracking

Also called: Sentry, exception monitoring, crash reporting, error alerts, GlitchTip

A service that catches unhandled errors in your server and browser code, groups repeats together, and alerts you with the stack trace. You learn about bugs before users report them. It also collects whatever data you let it, so set it up to avoid personal data.

You need it when

  • Any app with real users. Set it up before launch.

Skip it when

  • Prototypes nobody else uses yet.

Ways to build it

  1. Sentry free tier

    Install the SDK for your framework and set the DSN from an environment variable. Upload source maps for frontend errors.

    Tradeoff: The common choice, with SDKs for nearly everything. Sends data to a third party unless you self-host.

  2. Self-hosted and Sentry-compatible $0 + server

    GlitchTip accepts events from the Sentry SDKs and runs as a small Docker stack.

    Tradeoff: Your data stays on your server. Fewer features, and you run it.

  3. Your host's or log platform's errors varies

    Error views in your hosting dashboard or log platform, with alerts on error-level log lines.

    Tradeoff: Nothing new to install. Grouping and stack traces are usually weaker.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add error tracking to this app with [Sentry / GlitchTip].

Requirements:
- Initialize the SDK on the server and in the browser, only when the DSN environment variable is set.
- Don't send personal data: turn off default PII, don't send request bodies, cookies or local variables, and scrub emails, tokens and auth headers in a before-send hook.
- Tag each event with the release version and environment.
- Upload source maps for the frontend build, and don't serve them publicly.
- Alert me by email when a new kind of error appears or one spikes.
- Add a test route, available only to admins or in staging, that throws an error so I can confirm it arrives.

Acceptance checks (run each and show me the result):
1. The test error shows up in the dashboard with a readable stack trace.
2. The event has no email address, cookie, token or request body in it.
3. A frontend error shows original file names and lines, not minified code.
4. Each event shows the release version.

If you skip it

Bugs that silently hit users for weeks, or an error tracker that quietly collects passwords and personal data.

How Derek runs it

When a Sentry DSN is set, Custody Journal turns on Sentry with personal data off, no performance tracing, no local variables and no request bodies. A scrubber keeps only an allowlist (the event id, the exception class and in-app module, function and line) and breadcrumbs are dropped.
