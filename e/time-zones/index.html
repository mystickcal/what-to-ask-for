Time zone handling

Also called: UTC storage, IANA time zone, timestamptz, daylight saving time, DST bug, local time

Store moments in time as UTC, store each user's time zone as an IANA name like America/New_York, and convert only when you show a time or schedule one. An offset like -05:00 is not a time zone, because it changes with daylight saving.

You need it when

  • Users in more than one time zone, or any feature that says 'at 7 PM' or 'today'.
  • Daily limits, streaks, digests or reports that reset at midnight.

Skip it when

  • Rarely. Even a one-country app crosses a daylight saving change twice a year.

Ways to build it

  1. Your language's built-in zone support $0

    Python zoneinfo, JavaScript Intl.DateTimeFormat with a timeZone option, or java.time. Keep aware datetimes in UTC and convert at the edges.

    Tradeoff: No dependency. Date math across daylight saving is easy to get wrong without tests.

  2. A date library $0

    Luxon, or date-fns with date-fns-tz, in JavaScript. They handle zone-aware arithmetic like 'add one day in this zone'.

    Tradeoff: Clearer code for zone math. One more dependency in the bundle.

  3. Let the database convert $0

    Postgres timestamptz columns store an absolute moment. AT TIME ZONE 'America/New_York' converts in a query, for example to group rows by the user's local day.

    Tradeoff: Fast for reports. Spreads time logic across SQL and app code.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Fix time zone handling in this app.

Requirements:
- Store every timestamp as UTC (timestamptz in Postgres, aware datetimes in code).
- Add a time_zone field on the user that holds an IANA name like America/New_York. Validate it against the zone list and fall back to [default zone] when it is missing or invalid.
- Show times in the user's zone everywhere in the UI and in emails.
- For things a user schedules at a local time (like a 7 PM reminder), store the local time and the zone, then compute the next UTC run time from them. Don't store a fixed UTC hour.
- Daily limits, streaks and 'today' use the user's local day, not the server's.
- Add tests that cross the spring and fall daylight saving changes.

Acceptance checks (run each and show me the result):
1. A reminder set for 7:00 PM in New York fires at 7:00 PM local time on both sides of a daylight saving change.
2. A user in Tokyo and a user in Los Angeles each see an event at their own correct local time.
3. An invalid zone name falls back to the default instead of crashing.
4. A daily limit resets at the user's local midnight.
5. The database holds UTC values. Changing the server's time zone setting changes nothing users see.

If you skip it

Reminders drift an hour twice a year, daily limits reset at the wrong time, and dates near midnight show up on the wrong day.

How Derek runs it

Custody Journal stores times in UTC and keeps an IANA zone name on each user. A middleware switches to that zone on every request, old names like US/Eastern are mapped to their IANA names, and an invalid zone falls back to the default. The monthly AI allowance is counted by the month in the user's own zone.
