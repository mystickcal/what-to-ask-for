Server rendering for SEO

Also called: SSR, server-side rendering, static site generation, prerendering, SPA SEO, Lovable SEO

Sending finished HTML from the server, so the page's text and links are there before any JavaScript runs. Apps built as a single page with JavaScript, which is what many AI builders produce, send an almost empty page first. Search engines and link previews can miss the content, and AI crawlers often don't run JavaScript at all.

You need it when

  • You want public pages like the homepage, pricing, blog or docs to show up in search.
  • Viewing the page source shows an empty div and a script tag instead of your text.
  • Pages are listed in Search Console as discovered or crawled but not indexed.

Skip it when

  • Pages behind a login. Search engines can't see them anyway, so a JavaScript app is fine there.

Ways to build it

  1. A framework that renders on the server $0

    Next.js, Astro, Remix, SvelteKit or Lovable's TanStack Start upgrade render or pre-build pages as HTML.

    Tradeoff: The proper fix. Moving an existing app takes real work and testing.

  2. Pre-build only the public pages $0

    Make the marketing pages static HTML (a static site generator or a prerender plugin) and keep the app as is behind login.

    Tradeoff: Less to change. You now look after two parts of the site.

  3. Prerender service Free tier, then paid

    A service like Prerender.io serves a rendered copy to crawlers.

    Tradeoff: Works without changing the app. Another bill and another moving part, and the copy can go stale.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Make the public pages of this app render on the server so search engines see the full content.

Requirements:
- Public pages: [home / pricing / blog / docs / list them]. Leave pages behind login as they are.
- Use [Next.js / Astro / our framework's server rendering or static generation]. Keep the current design and URLs.
- Each public page gets its own title, meta description and canonical link in the HTML sent from the server.
- Generate /sitemap.xml with every public page and reference it in /robots.txt.
- Keep every existing URL working. If any URL must change, add a permanent redirect.

Acceptance checks (run each and show me the result):
1. Load each public page with JavaScript turned off in the browser. The main text, title and links are all there.
2. View the page source (not the inspector) of three public pages. Each has its own title, description and canonical link.
3. Google Search Console's URL Inspection shows the rendered page with its content for at least one page.
4. Open /sitemap.xml and /robots.txt. The sitemap lists every public page and robots.txt points to it.

If you skip it

Your pages can sit unindexed for months while you wonder why nobody finds you, and when they're shared the preview shows a blank title.

How Derek runs it

Custody Journal's public pages are rendered on the server by Django. /sitemap.xml is built with Django's sitemap framework, public pages carry canonical links, and the app strips the X-Robots-Tag header from the sitemap so search engines will read it.
