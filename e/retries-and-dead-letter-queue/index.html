Retries with backoff and a dead-letter queue

Also called: exponential backoff, retry policy, jitter, dead-letter queue, DLQ, failed jobs table, poison message

When a call to another service fails, try again after a wait that grows each time, with a little randomness so clients don't all retry at once. After a set number of attempts, park the job in a dead-letter queue or a failed state where a person can see it and replay it.

You need it when

  • A job or request calls something that can fail briefly: an email API, a payment API, an AI model, a webhook.
  • You have a background queue and need to know which jobs never finished.

Skip it when

  • The error will never fix itself, like a 400 for bad input or a 401 for a wrong key. Retrying those only adds load.

Ways to build it

  1. Retry settings in the queue you already run $0

    Celery (autoretry_for, retry_backoff, retry_jitter), BullMQ (attempts plus an exponential backoff option) and pg-boss (retryLimit, retryBackoff) all retry for you and keep failed jobs.

    Tradeoff: Least code. Check what each library does after the last attempt. Some just keep the failed job, and nothing alerts you unless you add it.

  2. A retry helper around single calls $0

    tenacity (Python) or p-retry (Node) wraps one function: stop after N attempts, wait exponentially with jitter, retry only on chosen exceptions.

    Tradeoff: Good inside one request or job. It doesn't survive a crash, so for important work put the job in a queue.

  3. A managed queue with a dead-letter queue free tiers or pay per use

    Amazon SQS redrive policies and Cloudflare Queues dead letter queues move a message aside after it fails a set number of times.

    Tradeoff: The dead-letter part is built in. Another service and account, and you still need an alert on the dead-letter queue.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add retries with backoff and a dead-letter state to [job or call].

Requirements:
- Retry only errors that can fix themselves: timeouts, connection errors, 429 and 5xx. Fail at once on other 4xx errors.
- Wait with exponential backoff plus random jitter, starting at [5 seconds] and capped at [10 minutes]. If the response has a Retry-After header, wait at least that long.
- Stop after [5] attempts. Then mark the job dead with a short error code and the attempt count. No stack traces or user data in that field.
- Make the work safe to run twice: use an idempotency key or check whether the effect already happened before redoing it.
- Add an admin view or command that lists dead jobs and replays one by id.
- Alert me when the number of dead jobs goes up.

Acceptance checks (run each and show me the result):
1. A fake API that fails twice and then succeeds ends with the job done and 3 attempts recorded.
2. A fake API that always returns 503 ends with the job marked dead after the max attempts, with growing gaps between attempts.
3. A 400 response is not retried.
4. A 429 with Retry-After: 30 waits at least 30 seconds before the next try.
5. Replaying a dead job by hand runs it once and does not repeat side effects that already happened.

If you skip it

One blip at a provider loses the email or the payment update for good, or tight retry loops pile onto a service that is already struggling.

How Derek runs it

Custody Journal sends sign-in emails from a database outbox. Each email gets at most 5 attempts, with waits of 15 seconds, 45 seconds, 2 minutes, 5 minutes and 10 minutes, and a worker holds a 2 minute lease while it sends. An email stops retrying when it reaches its attempt limit or when the next retry would land after the sign-in link expires.
