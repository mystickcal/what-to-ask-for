Idempotency keys for your API

Also called: Idempotency-Key header, safe retries, exactly once requests, duplicate request protection, request deduplication

The caller sends a unique key with each create request. Your API saves the key with the result, and if the same key comes back it returns the saved result instead of doing the work again. Retrying after a timeout becomes safe.

You need it when

  • POST endpoints that charge money, send messages or create orders.
  • Clients on flaky networks, like mobile apps, that retry automatically.

Skip it when

  • GET, PUT and DELETE that already give the same result when repeated.

Ways to build it

  1. An idempotency table $0

    Store (user, key, request hash, status, response) with a unique constraint. Insert first, do the work, save the response.

    Tradeoff: Reliable and simple. Needs cleanup of old keys after about a day.

  2. Middleware or a library $0

    Libraries for Express, NestJS, Django and Rails wrap endpoints and store keys in Redis or the database.

    Tradeoff: Quick. Check how each one handles two identical requests arriving at the same moment.

  3. Natural unique keys $0

    Use a unique constraint on a business value, like one invoice per (customer, month).

    Tradeoff: No header needed. Only works when such a value exists.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Make my create endpoints safe to retry with an Idempotency-Key header.

Requirements:
- Endpoints: [POST /orders, POST /payments]. Accept an Idempotency-Key header (UUID from the client).
- Store user id, key, a hash of the request body, status (in_progress, done), response code and body. Unique on (user id, key).
- If the key is new: insert as in_progress, do the work, save the response.
- If the key exists and is done: return the saved response with the same status code.
- If it exists and is in_progress: return 409 so the client retries later.
- If the body hash differs from the first request: return 422.
- Pass the same key to Stripe or any payment API you call.
- Delete keys older than [24 hours] in a scheduled job.
- Make the frontend and mobile app generate one key per user action and reuse it on retries.

Acceptance checks (run each and show me the result):
1. Sending the same request twice with one key creates one order and returns the same body both times.
2. Two identical requests sent at the same moment still create one order.
3. Reusing a key with a different body returns 422.
4. Killing the connection mid-request and retrying gives one order.
5. Keys older than the window are cleaned up.

If you skip it

Customers get charged twice or get duplicate orders every time the network hiccups.

People describe this as

  • “a retry created two payments”
  • “the client timed out but the order went through”
  • “make POST requests safe to retry”
  • “my mobile app sends the same request twice on bad wifi”
