Outgoing webhooks

Also called: webhooks you send, sending webhooks, webhook delivery, event notifications to customers, HTTP callbacks

Your app calls a URL your user gave you each time an event happens, like order.paid or report.ready. Done right, every delivery is signed, saved, retried with backoff and visible in a log, so a customer's slow server can't slow you down.

You need it when

  • Users want other tools (Zapier, Make, n8n, their own code) to react to events in your app.
  • Customers keep polling your API to ask if something changed.

Skip it when

  • No user has asked for integrations yet. A CSV export or email may be enough for now.

Ways to build it

  1. A deliveries table and your own worker $0

    Save one row per (endpoint, event) when the event happens. A background worker sends it, records the response code and schedules a retry on failure.

    Tradeoff: Full control and no vendor. You build the retry schedule, signing, logs and the customer-facing settings page yourself.

  2. A webhook delivery service free tier, then paid

    Svix or Hookdeck take your events and handle signing, retries, logs and an endpoint portal you can embed.

    Tradeoff: Saves weeks. Another vendor sees your event payloads and bills per message at volume.

  3. Queue plus a serverless sender free tiers

    Push events to a queue (SQS, Cloudflare Queues) and let a function deliver them with the queue's retry and dead-letter settings.

    Tradeoff: Scales well. Per-endpoint logs and a replay button are still yours to build.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add outgoing webhooks so users can subscribe a URL to events in my app.

Requirements:
- Users can add an endpoint (HTTPS only), pick which events it gets, and see its signing secret once.
- When an event happens, save a delivery row per endpoint in the same database transaction as the change. A background worker sends it.
- Body is JSON with id, type, created timestamp and data. Sign the timestamp plus body with HMAC-SHA256 and send the signature, timestamp and event id as headers.
- 10 second timeout. Don't follow redirects. Treat any 2xx as success.
- Retry failures with exponential backoff and jitter for about [8] attempts over a day, then mark the delivery dead.
- Block destinations that resolve to private, loopback or link-local addresses.
- Give users a delivery log (time, event, status code, attempt count) and a "resend" button.
- Disable an endpoint after [N] days of only failures and email its owner.

Acceptance checks (run each and show me the result):
1. A receiver can verify the signature with the secret and a 10-line script.
2. Pointing an endpoint at a server that returns 500 shows retries spreading out in the log.
3. An endpoint at http://127.0.0.1 or a private IP is rejected.
4. A receiver that sleeps 60 seconds does not hold up other deliveries.
5. Resending a delivery uses the same event id, so receivers can drop the duplicate.

If you skip it

Customers miss events whenever their server blips, nobody can tell what was sent, or your server gets used to probe internal addresses.

How Derek runs it

Custody Journal can send webhooks to URLs its users register. Each delivery is a saved row that a webhook worker sends with HMAC-SHA256 signatures, an event id that doubles as an Idempotency-Key header and a 10 second timeout. Failures retry with jittered backoff starting at 30 seconds and capped at 6 hours, for up to 8 attempts, then the delivery is marked dead. Destinations must be HTTPS, redirects aren't followed and private addresses are blocked.

From the Custody Journal code and release runbook, read 2026-10-21.
