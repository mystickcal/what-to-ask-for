API versioning plan

Also called: API versions, breaking changes, API deprecation, backward compatibility, v1 v2

A written rule for how your API changes over time: what counts as breaking, how a new version is chosen by callers, and how long old versions keep working. Adding fields is usually safe. Removing or renaming them is not.

You need it when

  • Anyone outside your own frontend calls your API, including your own mobile app that users don't update.

Skip it when

  • The API is only used by a web frontend you deploy at the same time.

Ways to build it

  1. Version in the URL $0

    /v1/orders and later /v2/orders. Old routes keep working until a published sunset date.

    Tradeoff: Obvious and easy to cache. Big jumps tend to bundle many changes at once.

  2. Dated versions per account $0

    Each account is pinned to the version it started on and can send a version header to upgrade. Small transform layers translate old shapes.

    Tradeoff: Smooth for customers, and it is the model Stripe documents. More code to keep each old shape alive.

  3. Additive changes only $0

    Never remove or rename. Add new fields and endpoints, mark old ones deprecated in docs and responses.

    Tradeoff: No version math. The API slowly collects leftovers.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Write and apply an API versioning plan for my API.

Requirements:
- List what counts as a breaking change (removing or renaming a field or endpoint, changing a type, new required input, changed error codes) and what doesn't (new optional fields, new endpoints).
- Use [URL versions like /v1/] and route all current endpoints under v1.
- Add Deprecation and Sunset headers to anything scheduled for removal, plus a changelog page.
- Keep contract tests that pin the v1 response shapes so an accidental break fails CI.
- Log which version each API key or app build uses, so I know who still calls old versions.
- Document the policy: how much notice before removal ([6 months]) and how customers are told.

Acceptance checks (run each and show me the result):
1. Renaming a field in a v1 response makes a contract test fail.
2. Deprecated endpoints return Deprecation and Sunset headers.
3. A dashboard or query shows request counts per version.
4. The changelog lists every breaking change with a date.
5. An old mobile build can still log in and load data.

If you skip it

One deploy breaks every customer integration and older app installs at once, with no warning.

People describe this as

  • “change my API without breaking customers' code”
  • “should I put v1 in the URL”
  • “rename a field in a public API”
  • “old mobile app versions still call the API”
