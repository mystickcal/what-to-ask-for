API docs from an OpenAPI spec

Also called: OpenAPI, Swagger, API reference, API documentation, SDK generation

One machine-readable file that describes every endpoint, field and error of your API. Reference pages, client libraries and contract tests are generated from it, so the docs can't drift far from the code.

You need it when

  • Anyone besides you calls your API, including AI agents and no-code tools.

Skip it when

  • Private endpoints used only by your own frontend.

Ways to build it

  1. Generate the spec from code $0

    FastAPI does it built in. drf-spectacular (Django REST), NestJS Swagger and zod-openapi build the file from your routes and schemas.

    Tradeoff: Stays in sync with the code. Descriptions and examples still need writing.

  2. Write the spec first $0

    Edit openapi.yaml by hand or in an editor, then generate server stubs and validate requests against it.

    Tradeoff: Forces design up front. Easy to let code and file drift without a CI check.

  3. A hosted docs platform free tiers, then paid

    Scalar, Redocly, Mintlify or ReadMe render the spec into searchable docs with a try-it console.

    Tradeoff: Polished fast. Monthly cost as you grow.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Publish accurate API docs for my API from an OpenAPI 3.1 spec.

Requirements:
- Generate the spec from the code with [tool for my framework], or write openapi.yaml if no generator fits.
- Every endpoint gets a summary, auth requirement, request schema, response schemas for success and each error, and one realistic example.
- Serve the reference at /docs with [Scalar or Redoc] and the raw file at /openapi.json.
- Add a CI step that fails when the spec is invalid or when the code and spec disagree (validate real responses in tests).
- Add a short "quick start" page: get a key, make one call with curl, read the response.
- Don't include internal or admin endpoints in the public spec.

Acceptance checks (run each and show me the result):
1. The spec passes a linter such as Redocly CLI or Spectral.
2. Changing a response field without updating the spec fails CI.
3. The curl example in the quick start works as pasted.
4. Admin endpoints are absent from /openapi.json.
5. An AI coding tool can call the API correctly from the spec alone.

If you skip it

Support time goes to explaining endpoints, and integrations break because the docs describe last month's API.

People describe this as

  • “customers keep asking how to call my API”
  • “write docs for my API”
  • “generate a client library for my API”
  • “my API docs are out of date”
