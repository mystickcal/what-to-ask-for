Soft delete and restore

Also called: trash, undo delete, archive, deleted_at, recycle bin

Marking a record as deleted instead of removing it, so it disappears from the app but can be restored. A purge job removes it for real after a set time, which also matters when someone asks you to erase their data.

You need it when

  • Users delete things they might want back.
  • Support keeps getting 'I deleted it by accident' requests.

Skip it when

  • The data is cheap to recreate, or must be gone at once for privacy reasons.

Ways to build it

  1. A deleted_at column and a default filter $0

    Add deleted_at, make the default query hide rows where it's set, and keep a separate way to reach all rows for admin and purge.

    Tradeoff: Simple. Every raw query, join and unique constraint has to remember the filter.

  2. A library $0

    django-safedelete, Rails' discard gem, or Prisma query extensions.

    Tradeoff: Less code to write. Learn how it treats related records.

  3. Move rows to an archive table $0

    On delete, copy the row to a trash table and delete the original. Restore copies it back.

    Tradeoff: Main queries stay simple. Restoring rows with relations takes more work.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add soft delete with restore to [model].

Requirements:
- Add deleted_at (nullable, indexed). Deleting sets it instead of removing the row.
- The default query everywhere hides deleted rows. Admin and the purge job use an explicit all-rows query.
- Unique constraints only apply to rows that aren't deleted (a partial unique index on Postgres).
- Add a Trash view where the owner can restore items within [30] days.
- A daily job permanently deletes rows that have been in the trash longer than [30] days, including their files.
- An account deletion request skips the trash and removes the data for good.
- Log who deleted and restored what.

Acceptance checks (run each and show me the result):
1. A deleted item disappears from lists, search and the API.
2. Restoring brings it back with its related data.
3. Creating a new item with the same unique name as a deleted one works.
4. After the retention period the purge job removes it and its files.
5. Grep shows no raw queries that skip the deleted filter.

If you skip it

Deleted items come back in search or counts, unique names stay taken forever, or 'deleted' data is still there when someone asks you to erase it.

How Derek runs it

Custody Journal's journal entries, custody events and communications share a soft-delete base with is_deleted and an indexed deleted_at. The default manager hides deleted rows, and a separate all_objects manager is used for admin, migrations and purging. Admin actions restore selected items, and soft deletes are written to the audit log.
