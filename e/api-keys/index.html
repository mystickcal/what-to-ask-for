API keys for your own API

Also called: personal access tokens, developer API keys, API tokens, secret keys, service tokens

Long random secrets your users create so their scripts can call your API without a password. You show the key once, store only a hash of it, and let users name, scope and revoke each one.

You need it when

  • Customers or their tools need to call your API from servers, scripts or no-code tools.

Skip it when

  • Only your own frontend calls the API. Use normal login sessions.
  • Third-party apps act on behalf of users. That calls for OAuth, not pasted keys.

Ways to build it

  1. Hashed keys in your own table $0

    Generate 32 random bytes with a readable prefix like myapp_live_. Store a SHA-256 hash, the last 4 characters, scopes, created and last-used times.

    Tradeoff: Simple and safe. You build the settings page, scopes and usage tracking.

  2. An API key service free tier, then paid

    Unkey or Zuplo issue, verify and rate limit keys for you, with per-key analytics.

    Tradeoff: Fast to ship. Every API call now depends on their verify step.

  3. Your auth provider's machine tokens depends on plan

    Some auth providers (Clerk, WorkOS, Auth0) offer API keys or machine-to-machine tokens tied to your users or orgs.

    Tradeoff: One less system. Features and limits vary a lot by plan.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add API keys so users can call my API from their own code.

Requirements:
- Settings page: create a key with a name and scopes ([read], [write]), list keys (name, prefix, last 4, scopes, created, last used) and revoke.
- Key format: a fixed prefix like [myapp_live_] plus at least 32 random bytes, base62 or base64url.
- Show the full key exactly once. Store only a SHA-256 hash and look keys up by that hash.
- Accept keys in the Authorization: Bearer header only, never in the URL.
- Check scopes on every endpoint. Revoked keys fail right away.
- Rate limit per key, and update last_used_at at most once a minute.
- Log key creation and revocation in the audit log.
- Never log full keys. Add the prefix pattern to secret scanning if the host supports it.

Acceptance checks (run each and show me the result):
1. The database has no column that holds a usable key.
2. A revoked key gets 401 on the next request.
3. A read-only key gets 403 on a write endpoint.
4. A key passed in the query string is refused.
5. Request logs show the key prefix, never the full key.

If you skip it

A database leak hands out working keys for every customer, or a leaked key can't be shut off without breaking everyone.

How Derek runs it

Custody Journal's mobile app tokens follow the same storage rule: the database keeps only a SHA-256 hash of each token, plus an expiry time.
