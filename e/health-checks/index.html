Health checks and safe deploys

Also called: health endpoint, readiness probe, liveness probe, healthz, zero-downtime deploy, rolling deploy

Small URLs your platform calls to ask two things: is the process alive (liveness), and can it serve traffic right now, with the database, cache and migrations in order (readiness). Deploy tools wait for readiness before sending traffic to a new version and keep the old one if it never gets there.

You need it when

  • Anything with users, and any automated deploy.

Skip it when

  • Rarely. Even a hobby app benefits from a readiness check and an outside uptime ping.

Ways to build it

  1. Two endpoints in your app $0

    /health/ (process up, no dependency calls) and /health/ready/ (database, cache, schema). Point Docker HEALTHCHECK, Coolify health checks or Kubernetes probes at the readiness one.

    Tradeoff: A readiness check that tests too much can flap and take the site down on a minor issue.

  2. Health-gated rolling or blue-green deploys $0

    Start the new container, wait for readiness, switch the proxy, then stop the old one.

    Tradeoff: Needs database migrations that work with both the old and new code at once: add columns first, remove them in a later release.

  3. Outside monitoring free tiers or self-hosted

    An uptime checker for the site, and Healthchecks.io (open source) for alerts when a scheduled job stops checking in.

    Tradeoff: Tells you something broke. It doesn't stop a bad deploy.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add health checks and a health-gated deploy for this app.

Requirements:
- GET /health/ returns 200 when the process is running. No database calls.
- GET /health/ready/ checks the database (SELECT 1), the cache (set and read a short-lived key) and pending migrations. It returns 200 with per-dependency status JSON, or 503 if any fail. No secrets, versions or hostnames in the response.
- The container health check points at /health/ready/.
- Deploy: start the new version, wait until /health/ready/ returns 200 (timeout [90 seconds]), then switch traffic. If it never gets ready, keep the old version serving.
- Migrations in this release must work with the currently running code.

Acceptance checks (run each and show me the result):
1. Stopping the database makes /health/ready/ return 503 within a few seconds while /health/ stays 200.
2. Deploying a build that crashes on start leaves the old version serving.
3. During a normal deploy, a curl loop every half second sees no 5xx responses (if zero downtime is the goal).
4. The health response contains no secrets or internal hostnames.
5. Health check traffic is excluded from analytics and rate limits.

If you skip it

Every deploy causes a few minutes of errors, and a bad build stays live until someone notices.

How Derek runs it

Custody Journal exposes /health/ready/, which reports database, cache and schema status. Its releases are not zero-downtime: the runbook uses a short maintenance window, says not to use the Coolify Deploy button (that redeploy replaces the whole stack, including Postgres and Redis), and doesn't end maintenance until all six services are healthy and /health/ready/ returns 200. If any health gate fails, the release guard runs the captured rollback automatically.

People describe this as

  • “the site goes down every time I deploy”
  • “know my app is broken before users tell me”
  • “the new version started before the database was ready”
  • “roll back automatically if the deploy is bad”
