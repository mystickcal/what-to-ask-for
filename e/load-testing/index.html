Load testing

Also called: stress testing, performance testing, k6, Locust, capacity planning

Sending realistic fake traffic at a copy of your app to find where it slows down or breaks: requests per second, response times at the 95th percentile, errors, and which part (database, CPU, an outside API) gives out first.

You need it when

  • Before a launch, a big email send or a sale.
  • After changing infrastructure or adding a heavy feature.

Skip it when

  • You have a handful of users and no launch planned. Real traffic will tell you more.

Ways to build it

  1. k6 $0 open source, paid cloud

    Write user journeys in JavaScript, ramp virtual users up, and set pass or fail thresholds for latency and errors.

    Tradeoff: Good scripting and thresholds for CI. Browser-level tests are heavier.

  2. Locust $0

    Python classes describe user behavior. A web UI shows live results.

    Tradeoff: Easy for Python teams. Needs more machines for very high loads.

  3. Artillery or a simple HTTP tool $0 open source

    Artillery YAML scenarios, or oha and hey for quick single-endpoint blasts.

    Tradeoff: Fast to start. Single-endpoint tests miss real user flows.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Load test my app before [launch] with [k6 / Locust].

Requirements:
- Test a staging copy with production-like data size, never production with real users.
- Script 3 journeys: [anonymous home page visit], [sign up and first action], [the heaviest logged-in page or API].
- Ramp from 1 to [expected peak x 3] virtual users over 10 minutes, then hold.
- Thresholds: 95th percentile under [500 ms], error rate under 1%.
- Stub or sandbox outside services (payments, email, AI) so the test doesn't hit them or cost money.
- While it runs, watch CPU, memory, database connections and slow queries. Note what fails first.
- Report: max users before thresholds broke, the bottleneck, and the top 3 fixes.

Acceptance checks (run each and show me the result):
1. The test runs against staging, not production.
2. No real emails, charges or AI calls happened during the test.
3. The report names the first bottleneck with evidence (graph or slow query).
4. Thresholds fail the run when crossed.
5. Rerunning after a fix shows the change.

If you skip it

The launch day traffic you worked for turns into timeouts, and you find the bottleneck live.

People describe this as

  • “will my app survive a launch on Product Hunt”
  • “how many users can my server handle”
  • “the site slowed down when 200 people signed up at once”
  • “find the bottleneck before going viral”
