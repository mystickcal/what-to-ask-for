Magic link sign-in

Also called: passwordless login, email link login, sign in with email, one-time login link

The user types their email and gets a link that signs them in. The link holds a random one-time token that expires in minutes. Email security scanners often open links before the person does, so a safe design shows a confirm button and only signs in on that click.

You need it when

  • You don't want to store passwords, or your users forget them often.

Skip it when

  • Users sign in many times a day on shared machines, where waiting for an email is painful.

Ways to build it

  1. Your auth provider free tiers

    Supabase Auth, Clerk and Auth.js (the Email provider) send and check magic links.

    Tradeoff: Quick. Check how each one handles link scanners and expiry.

  2. A framework package $0

    django-sesame for Django. Other frameworks have similar packages.

    Tradeoff: Less code. Read its defaults for expiry and single use.

  3. Your own tokens table $0

    Store a SHA-256 hash of a random token with an expiry and used_at. The link opens a page with a 'Sign in' button that POSTs the token.

    Tradeoff: You control every rule. You also own the email delivery and rate limits.

Prompt for your coding agent

Add magic link sign-in.

Requirements:
- The form takes an email and always shows the same message: 'If an account exists, we sent a link. It expires in [15] minutes.'
- Rate limit per IP and per email.
- Token: 32 random bytes from a secure generator. Store only its hash with expires_at and used_at. A new request deletes older unused tokens for that user.
- The link opens a confirm page (GET changes nothing). The user clicks 'Sign in', which POSTs the token with CSRF protection.
- On POST, in one transaction: lock the token row, check it is unused and unexpired, mark it used, then log the user in.
- The confirm page sends Cache-Control: no-store and Referrer-Policy: same-origin and loads no analytics.
- Only allow a 'next' redirect to our own site.

Acceptance checks (run each and show me the result):
1. Fetching the link with curl (like a scanner would) doesn't use up the token.
2. Clicking 'Sign in' works once. A second POST with the same token fails.
3. A link older than the expiry fails with a friendly message.
4. Requesting a link for an unknown email looks the same as for a known one.
5. A next=https://evil.example parameter is ignored.

If you skip it

Links get burned by email scanners, old links stay valid, or a link in a forwarded email signs in a stranger.

How Derek runs it

Custody Journal's sign-in links expire in 15 minutes. It stores only a SHA-256 hash of each token, and a new request deletes the user's older unused links. Opening the link shows a confirm page with no analytics, no caching and a same-origin referrer policy. Only the CSRF-protected POST uses the token, and it marks the token used inside a locked transaction before logging in. Requests are limited to 8 per IP and 3 per email per hour, and the reply is the same whether or not the account exists.
