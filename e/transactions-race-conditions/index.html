Transactions and race conditions

Also called: race condition, database transaction, row locking, select for update, double submit, atomic update

Making a group of database changes all happen or none happen, and making sure two requests running at the same moment can't both pass a check that only one should pass. Check-then-write code is the usual bug: both requests read the old value before either writes.

You need it when

  • You check a balance, quota, stock count or 'already used' flag and then change it.
  • One action writes to more than one table.

Skip it when

  • Single writes with no check before them, like saving a draft.

Ways to build it

  1. Atomic conditional updates $0

    Do the check inside the write: UPDATE accounts SET credits = credits - 1 WHERE id = ? AND credits >= 1, then see whether a row changed.

    Tradeoff: Fast, no locks held. Only fits checks that one statement can express.

  2. Transaction with a row lock $0

    Open a transaction, SELECT ... FOR UPDATE the row that guards the rule (the user, the account), check, write, commit.

    Tradeoff: Handles complex rules. Keep it short, and lock rows in the same order everywhere to avoid deadlocks.

  3. Unique constraints and idempotency keys $0

    A unique index on (user_id, request_key) or on the natural key makes the second insert fail. The client sends the same key on a retry.

    Tradeoff: Stops duplicates even across servers. Needs a key the client keeps for the action.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Find and fix race conditions in [feature, e.g. credits, checkout, invites].

Requirements:
- List every place that reads a value, checks it, then writes based on it (balances, quotas, stock, 'used' flags, unique names).
- Fix each with a conditional update, a row lock inside a transaction, or a unique constraint. Say which and why.
- Wrap multi-table writes in one transaction.
- Give create actions an idempotency key so a double click or retry doesn't create two records.
- Disable the submit button while a request is in flight, but don't rely on it.
- Write a test that fires [20] parallel requests at each fixed action.

Acceptance checks (run each and show me the result):
1. 20 parallel 'spend 1 credit' requests on a balance of 5 leave exactly 0 and succeed 5 times.
2. Double clicking 'Place order' creates one order.
3. Killing the process halfway through a multi-table write leaves no partial data.
4. Parallel requests can't push a free account past its limit.

If you skip it

Negative balances, duplicate orders and charges, free limits that a script can beat, and half-saved records.

How Derek runs it

Custody Journal checks the free plan's monthly entry limit while holding a row lock on the user (select_for_update), so parallel requests can't both use the last slot. A sign-in link is marked used with a conditional update that only succeeds while it's still unused and unexpired, so it can't be used twice.
