Feature flag

Also called: feature toggle, kill switch, gradual rollout, dark launch, flag

A named on and off switch the code checks at runtime. You deploy with the feature off, turn it on for everyone, some users or just yourself, and turn it off fast if it breaks.

You need it when

  • Risky changes, payment changes, anything you want to undo without a rollback.
  • You want to try something in production before users see it.

Skip it when

  • Small fixes. Every flag is a branch in your code that you have to remove later.

Ways to build it

  1. Environment variable flags $0

    Read FEATURE_X_ENABLED at startup.

    Tradeoff: Dead simple. Changing a flag needs a restart or redeploy, and it is all or nothing.

  2. A flags table with an admin switch $0

    django-waffle, Flipper for Rails, or your own table with a cached lookup.

    Tradeoff: Flip without deploying and target staff or a list of users. More code, and the lookup needs caching.

  3. A flag service free tiers or self-hosted

    Unleash and GrowthBook are open source and self-hostable. PostHog also has feature flags.

    Tradeoff: Percent rollouts and targeting built in. Another service and SDK in your stack.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Put [feature] behind a feature flag named [flag_name].

Requirements:
- Default off in every environment.
- One helper, is_enabled(flag, user), used everywhere. No scattered environment reads.
- Support three states: off, on for everyone, on for a list of staff user ids.
- When off: the feature's routes return 404, its UI is hidden and its scheduled jobs skip.
- Log flag changes with who and when.
- Add a dated TODO to remove the flag once it has been fully on for a while.

Acceptance checks (run each and show me the result):
1. With the flag off, the feature can't be reached by URL.
2. Turning it on for one staff user shows it only to them.
3. Turning it off hides it again without a code change.
4. Tests cover both the on and off states.
5. Scheduled jobs for the feature do nothing while it's off.

If you skip it

Every risky change becomes a full rollback, and half-built features leak to users.

How Derek runs it

Custody Journal uses environment flags (for example CJ_BILLING_MEASUREMENTS_ENABLED) set per service in a small Compose override file that each release must include. Its release guard compares environment keys between the live and new stack and aborts on any flag change that isn't named in an explicit allow rule for one service, one key and one exact change.

  • “let only me test it in production”
  • “roll a feature out to some users first”
