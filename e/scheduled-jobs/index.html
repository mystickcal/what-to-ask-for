Scheduled job

Also called: cron job, scheduled task, recurring job, periodic task, job scheduler

Code that runs on a clock instead of when someone clicks. A scheduler wakes up, checks what is due and runs it.

You need it when

  • Something has to happen when nobody is on the site: reminders, digests, cleanup, syncing.
  • A user picks a time and expects something to arrive then.

Skip it when

  • The work can run right when the user clicks and finishes in a second or two.

Ways to build it

  1. Cron or supercronic calling a command $0

    A crontab line (or supercronic inside a container) runs one command on a schedule, like a Django management command or a Node script.

    Tradeoff: If the server is down at 3 AM, that run is simply lost unless you add catch-up. Two copies of the container means every job runs twice.

  2. A scheduler inside your worker $0 on your server

    Celery beat (Python), BullMQ repeatable jobs (Node) or pg-boss schedules (Postgres) enqueue jobs on a schedule for your workers.

    Tradeoff: One more process to keep alive, and you need a lock so only one instance does the scheduling.

  3. A managed trigger that calls your URL free tiers

    Cloudflare Workers Cron Triggers, Vercel Cron Jobs or a GitHub Actions schedule hits an endpoint on your app.

    Tradeoff: The endpoint is public, so it needs a secret check. Timing can drift, and GitHub notes scheduled workflows can be delayed under load.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Add a scheduled job that [does X] every [schedule], in UTC.

Requirements:
- Put the job logic in one function or command that I can also run by hand.
- Record each run in the database: job name, scheduled slot, started, finished, status, error code.
- Make (job name, scheduled slot) unique so the same slot never runs twice, even if two scheduler processes start.
- If the scheduler was down, catch up missed slots inside a [2 hour] window and skip older ones.
- Give each run a timeout and a max attempt count.
- Store and compare times in UTC. Convert to the user's timezone only for display and for user-picked send times.

Acceptance checks (run each and show me the result):
1. Running the command by hand twice for the same slot does the work once.
2. Starting two scheduler processes at the same time still runs each slot once.
3. Stopping the scheduler for 10 minutes and restarting it runs the missed slot once.
4. A run that passes its timeout is marked failed and the next slot still runs.
5. A user who picked 7:00 PM in New York gets it at 7:00 PM New York time across a daylight saving change.

If you skip it

Reminders silently stop after a restart, or every user gets the same email twice when you scale to two containers.

How Derek runs it

Custody Journal runs its own UTC scheduler in a separate operations container. Every job has a schedule, a catch-up window, a timeout and a max attempt count. Each run claims its time slot in a database row with a row lock, so one slot can't run twice. Examples from the job list: transactional mail every minute and a subscription reconcile once a day.

From the Custody Journal code and release runbook, read 2026-10-21.

  • “send a reminder the day before”
  • “clean up old files every hour”
  • “sync with another service every few minutes”
