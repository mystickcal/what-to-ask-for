Keeping a search index in sync

Also called: search indexing jobs, reindexing, Meilisearch sync, Algolia sync, index updates

The jobs that copy changes from your database into a separate search engine. Every create, update and delete queues an index update, a full rebuild can run into a fresh index and swap over, and a check catches drift.

You need it when

  • Search runs on a separate engine (Meilisearch, Typesense, Algolia, Elasticsearch, OpenSearch) or a vector store.

Skip it when

  • Search runs inside your main database (Postgres full-text), so it's always current.

Ways to build it

  1. Queue an index job on every change $0

    After commit, enqueue upsert or delete jobs with the record id. The job reads the current row and updates the index.

    Tradeoff: Near real time. Missed jobs leave drift unless you also reconcile.

  2. Library-managed sync $0

    Laravel Scout, Rails searchkick or meilisearch-rails, and similar packages hook into model saves.

    Tradeoff: Little code. Bulk updates and raw SQL can skip the hooks.

  3. Full rebuild with an alias swap $0

    Build a new index from scratch, then point the alias or swap indexes in one step.

    Tradeoff: Fixes all drift and schema changes with no downtime. Takes time and resources on big data.

Prompt for your coding agent

Replace the [bracketed] parts. Works in Claude Code, Cursor or Codex.

Keep my [Meilisearch / Typesense / Algolia] index in sync with the database.

Requirements:
- After a transaction commits, enqueue index jobs for created, updated and deleted records (soft deletes and permission changes count as removals).
- The job loads the current row and upserts or deletes, so out-of-order jobs end up correct.
- Batch updates when many records change at once.
- A rebuild command: create a new index, fill it in batches, then swap it in with no search downtime.
- A nightly reconcile that compares ids and updated_at between database and index and fixes differences.
- Only index fields that are safe to show. Filter results by owner or tenant in every search query.
- Metrics: queue length, failed jobs and drift count.

Acceptance checks (run each and show me the result):
1. A deleted record disappears from search within a minute.
2. Editing a title shows the new title in results.
3. Running the rebuild while searching causes no errors or empty results.
4. Breaking the worker for an hour, then fixing it, leaves no drift after reconcile.
5. A user never sees another tenant's records in results.

If you skip it

Search shows deleted or private items and misses new ones, and users stop trusting it.

People describe this as

  • “search results show things I already deleted”
  • “new items don't show up in search”
  • “rebuild the search index without downtime”
  • “keep Algolia in sync with my database”
